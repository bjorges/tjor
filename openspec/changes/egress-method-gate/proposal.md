# Proposal

## Why

Egress rules match host and path only: `tjor_policy.evaluate(policy, url)` never sees the HTTP method, and a rule entry has exactly the keys `host` and `path` (#66). Two consequences follow for anyone who brokers a credential into the cage. A token whose server-side scope is broader than the session needs — most SaaS API tokens carry the user's full permissions — cannot be narrowed to reads at the proxy, which is the one place tjor controls (ADR 0007: the agent holds a placeholder, the proxy holds the secret, so the proxy is where "read-only" has to be enforced). And "read-only" is not even expressible for APIs that query by POST (search endpoints commonly do): adding a method to the existing path rules would not help, because path allow carve-outs only rescue a host-blocked host and stage-2 path blocks have no exception mechanism. The result today is that a brokered credential is as powerful inside the cage as it is outside, and the only lever is to not broker it.

Grounding the review of this plan in `proxy/addon.py` and the pinned mitmproxy (12.1.2) source surfaced two enforcement gaps the gate would inherit. They already weaken today's path rules and credential injection, so they are fixed here, as their own requirements:

- **Enforcement runs after the body.** The addon decides in mitmproxy's `request` hook, which fires once the whole body has been read. With `stream_large_bodies=1m` (compose.yaml) a request whose declared body exceeds 1 MiB, or whose chunked body grows past it, is streamed: mitmproxy sends its headers upstream *before* `request` fires. For such a request a path block answers 403 only after the request has been delivered, and the broker, gateway and identity handling in the same hook come too late: the upstream receives the agent's placeholder `Authorization` and any forged `x-agent-*` header. A `git push` of a pack over 1 MiB toward a brokered host, or a large inference request toward the gateway, hits this today.
- **Policy and injection use different host identities.** The verdict is computed on `flow.request.pretty_url`, whose host is the client's `Host` (`:authority`) header; injection keys on the TLS SNI (ADR 0007). Inside a tunnel to host A, an inner request with `Host: B` is judged under B's rules and sent to A carrying A's credential. A method gate keyed on the same URL would be bypassed the same way.

## What Changes

- **A method gate in the egress policy.** A new top-level `methods` section with two rule kinds: `[[methods.restrict]]` (`host`, `allow = [<METHOD>, …]`) denies every method on a matching host that is not listed by every matching rule; `[[methods.except]]` (`host`, `path`, `methods = [<METHOD>, …]`) admits a listed method on exactly that path, matched like an allow rule (every encoded and decoded form of the path must match, charter L22). The gate runs **after** the existing stages, on a request they allow, and can only turn that allow into `method-block:<METHOD>`: a request the earlier stages deny is reported by the stage that denied it, a request the gate admits keeps the earlier verdict, and an absent `methods` section yields today's verdicts.
- **The method is an exact HTTP token.** It is compared byte for byte as the agent sent it — no case folding, no trimming — and must be an RFC 9110 token of 1 to 32 ASCII characters; anything else is denied with `fail-closed:bad-method` on every host. `evaluate` takes the method with no default, so a call site that forgets it fails in the first test run instead of evaluating a POST as a GET. `evaluate_connect` is unchanged: CONNECT is decided on the host, and each request inside the tunnel is evaluated with its own method.
- **Header guards on restricted hosts.** On a host matched by a restrict rule, the proxy denies a request carrying an `Upgrade` header (`method-block:upgrade`: a GET that becomes a duplex channel is not a read) or a method-override header (`method-block:override-header`). Unrestricted hosts are unaffected.
- **Enforcement moves to the headers stage.** The verdict, the denial, credential injection and identity handling run in mitmproxy's `requestheaders` hook, before any part of the request can be sent upstream. A denied request receives a 403 when the proxy can answer without buffering more than the streaming threshold, and otherwise has its stream closed; in both cases no request byte reaches the upstream and the denial is logged. A streamed allowed request now carries the real credential and stripped identity headers.
- **One host identity.** A request is judged on the host its connection was opened to: the CONNECT target for a tunnelled request (which must equal the SNI), the URL host otherwise. The `Host` or `:authority` header must name the same host; a mismatch is denied with `fail-closed:host-mismatch`. The same host keys injection and the resolved-address guard.
- **Every call site passes the method, and the parity suite checks it.** The addon passes the method as sent; `tjor policy <url>` gains `--method <M>` (default `GET`, so today's invocations keep their meaning); the shared corpus carries a method on every case and gains method cases (charter L4). A method denial reads `method-block:<METHOD>` in the 403, the denial log and `tjor denials`, which, like the teardown recap, points at `[[methods.except]]` rather than `tjor policy add` for such lines.
- **Policy tooling keeps the section intact.** The gateway's policy augmentation parses and validates the base policy with the policy parser first — an invalid base policy fails the launch loudly instead of being re-emitted without its malformed section — re-emits the `methods` rules, and adds POST exceptions for the gateway's POST inference paths so a broad restrict cannot break tjor's own inference host. `tjor policy add` inserts into `hosts.allow` only, never into a restrict rule's `allow` list.
- **Docs and proof.** A read-only-API example and a read-only-git example in the README and the packaged default policy (commented out, so the default verdicts do not change), with the stated limits; conformance probes for the gate, the header guards, the headers-stage enforcement and the host identity on the Linux engine; the egress-policy, policy-ergonomics and llm-gateway specs amended and their slides re-read; a short ADR for the enforcement point and the host identity.

Compatibility. A policy without a `methods` section evaluates as before for every request whose method is an HTTP token. Four behaviours change for operators, all in the fail-closed direction: a request whose `Host`/`:authority` disagrees with the host its connection was opened to is denied (no known client does this); a request whose method is not an HTTP token is denied; a denied request with a large or chunked body may see a closed connection instead of a 403; a policy that fails to parse with the gateway enabled fails the launch rather than starting a deny-everything session. Breaking for the Python API only: `evaluate` and `check` require a method; every in-repo caller is updated.

### Modified Capabilities
- `egress-policy`: the precedence requirement gains the method gate as the final, deny-only stage; new requirements state the restriction and exception semantics, the exact-token method, the header guards on restricted hosts, enforcement before any request byte reaches the upstream, one host identity for verdict and injection, and the stated limits; the fail-closed requirement covers a malformed `methods` section; the parity requirement's corpus carries the method.
- `policy-ergonomics`: `tjor policy <url>` accepts `--method`; the denial log and `tjor denials` show the refused method and give the right widening hint; the teardown recap distinguishes method denials.
- `llm-gateway`: the session policy augmentation derives from the validated base policy and preserves every section; the gateway's POST inference paths stay reachable under method restrictions.
