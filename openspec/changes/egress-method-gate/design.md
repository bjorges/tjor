# Design

## Context

See proposal.md — Why. What exists today, verified in the code and in the pinned mitmproxy (12.1.2, `config/tjor.toml`) source, and shapes the approach:

- `python/tjor_policy.py` is the single matcher (charter L4). `parse_policy` is strict: `_TOP_KEYS = {mode, hosts, paths}`, a rule entry has exactly `{host, path}`, and any unknown key or wrong type makes the whole policy `valid=False`, which `evaluate` and `evaluate_connect` turn into deny-everything. `evaluate(policy, url)` runs: invalid policy → bad URL → excessive encoding → host blocklist, where a matching block pattern either returns an all-forms carve-out allow or a `host-block` deny → any-form path blocks → default mode. That precedence is spec'd and tested.
- `Verdict.rule` names the deciding stage and carries detail after a colon where there is detail: `fail-closed:bad-url`, `ip-guard:<why>`, `connect-defer:carveout`. The 403 body and the `x-tjor-rule` header show the rule; the session denial log is `host\trule\ttime` at `${TJOR_SESSION_DIR}/denials.log` on the host; `tjor denials` prints it as is and the teardown recap reads only the host column. Both end with "allow what you need with: tjor policy add <host>" (`bin/tjor` cmd_denials, the teardown recap).
- Three call sites: `proxy/addon.py` (`decide(url)` from `request_verdict(url, host)`, called by the `request` hook with `flow.request.pretty_url`; `decide_connect(host)` from `http_connect`), the `tjor_policy.py check` CLI behind `tjor policy <url> [--explain]` (whose argument loop strips only `--explain`, so `--method POST` would be read as the URL), and the module API used by tests, `tjor_gateway` and `tjor_policy_edit`. `evaluate(` is called 19 times in `test_policy.py`, 9 in `test_gateway.py`, 4 in `test_config_ergonomics.py`; `test_addon_guards.py` calls `request_verdict` with two arguments at five places and stubs `decide` as `lambda url:` once. `python/tests/test_parity.py` runs `python/tests/fixtures/corpus.json` (21 URL cases, no method) against all three.
- The addon's `request` hook does everything: verdict, 403, then for an allowed request identity handling, broker and gateway injection, and the #62 body scan. mitmproxy fires `request` once the whole body has been read. In `state_wait_for_request_headers`, `check_body_size` runs *before* the `requestheaders` hook and sets `flow.request.stream = True` when the declared body exceeds `stream_large_bodies` (1 MiB in compose.yaml); right after the hook, `start_request_stream` opens the upstream connection and sends the request headers, then streams the body, and only then fires `request`. A chunked body has no declared size, so it is buffered and streaming starts, headers first, once the buffer passes the threshold. `start_request_stream` raises `NotImplementedError` if a response has been set on a streaming flow; `server.py` logs that as "mitmproxy has crashed!" for the event and carries on, so every further body frame of such a flow raises again. `requestheaders` therefore is the last point at which nothing has gone upstream, and the only hook at which a 403 or a kill (`flow.kill()` → `check_killed` → the HTTP/1 connection is closed without a response) can prevent delivery for every request shape.
- The declared size comes from `expected_http_body_size`: `None` for a chunked request, the `Content-Length` when there is one, else `0`. Over HTTP/1.1 that is exact, because mitmproxy's reader reads exactly that much and `validate_inbound_headers` (on by default) rejects any other framing. Over HTTP/2 a request with no `Content-Length` reports `0` while DATA frames may still follow the headers, so the hook cannot tell an empty body from an unbounded one; the `h2` library (4.3.0) does reset a stream whose DATA exceeds a declared `Content-Length`. With `http2=false` mitmproxy's `alpn_select_callback` chooses only among the HTTP/1 ALPN values and offers only those upstream; a client offering only `h2` gets no overlapping protocol. mitmproxy loads `config.yaml` from its confdir (`/home/mitmproxy/.mitmproxy`, the session's `proxy-ca/` mount) at start.
- `flow.request.method` is mitmproxy's `.upper()` of the raw method bytes (`http.py`); the raw bytes are `flow.request.data.method` and are what goes upstream. mitmproxy's HTTP/1 request-line reader splits on whitespace and validates only the HTTP version, so a non-token method reaches the addon unchanged.
- `flow.request.pretty_url` builds its host from `Host`, which mitmproxy's own docstring calls spoofable in adversarial settings. Inside a CONNECT tunnel the inner HTTP layer runs in transparent mode, so `flow.request.host` is the tunnel's server address (the #41 pinned IP after `server_connect`) and the verified TLS server name is `flow.server_conn.sni`; `_logical_host` already keys injection on that SNI (ADR 0007) and falls back to `pretty_host`. For a request sent directly to the proxy (absolute-form, plain HTTP) `flow.request.host` is the URL's host from the request line; mitmproxy clears `authority` on HTTP/1 before the hooks run, so `first_line_format` cannot tell the two shapes apart, but `flow.client_conn` is the same object (with a stable `id`) for a CONNECT flow and every flow inside its tunnel.
- `python/tjor_gateway.py` `augment_policy` re-reads the base policy with `tomllib` and a tolerant shape (malformed rules and unknown keys are skipped), then writes `mode`, `hosts` and the two `paths` lists. `bin/tjor` `ensure_topology` copies the base policy to `${TJOR_SESSION_DIR}/policy.toml` first, augments that copy, and validates only the augmented output; `tests/integration/gateway_test.sh` sources `bin/tjor` and reproduces the augmentation by calling the Python CLI, not `ensure_topology`. A base policy with `allows = [...]` under `[[methods.restrict]]`, or `[[methods.restirct]]`, would come out valid and unrestricted. The gateway's inference paths are carved in as `paths.allow` on the gateway host, which sits in `hosts.block`; four of them are POST-only in practice (`/chat/completions`, `/completions`, `/embeddings`, `/messages`, with and without `/v1`), `/models` and the health paths are GET.
- `python/tjor_policy_edit.py` inserts new hosts after the first `allow = [` that follows `[hosts]`, anywhere in the file, and otherwise appends a new `[hosts]` table; a second `[hosts]` table is a TOML error, and a restrict rule has an `allow` list of its own.
- The conformance suite (19 probes today) runs `images/conformance/probes.py` inside the cage against `images/conformance/policy.toml`; `via_proxy` sends absolute-form GETs; `is_policy_deny` is "403 with `x-tjor-policy: deny`" and does not look at the rule; `p_rawtcp_disabled` shows that a plain CONNECT tunnel to the echo fixture needs no CA. The egress-side echo fixture (`images/conformance/echo.py`) answers GET only, over plain HTTP, and reflects headers; it is reachable through the proxy under compose aliases on the egress network. The conformance container (`python:3.13-slim`, stdlib only) is not given the proxy CA; only the agent service mounts `ca.pem`. The launcher pre-generates the proxy CA with the host's `openssl` (so that is a host dependency already) and copies the certificate to `${TJOR_SESSION_DIR}/ca.pem`. `cmd_conformance` reads the probe summary from the run's output and removes the session directory in its EXIT trap. Every probe name is registered in `python/gen_boundary_matrix.py`; `tests/doc_consistency.sh` fails when the registry and the probe sources disagree or `docs/boundary-matrix.md` is stale.
- `python/gen_corefile.py` derives DNS zones from `host_allow` only; the broker and identity modules use `host_matches` only. None of them evaluates a request.

## Goals / Non-Goals

**Goals:**
- A restrict/except pair in the policy that can only narrow, with the same encoding asymmetry as the path rules, evaluated by the one matcher and proven at all three call sites.
- No silent path by which a restriction is lost: not by a call site that forgets the method, not by the gateway augmentation, not by `tjor policy add`, not by a header that changes what the verb means (`Upgrade`, method override), not by a body that is streamed before the verdict, not by a `Host` header that names another host, not by a transport whose framing hides the body from the headers stage.
- The refused method visible wherever a denial is visible, with a hint that leads to the right fix, and a header-guard denial with a hint that says it has no exception.
- Conformance probes that prove the gate, the header guards, the enforcement point (with an upstream that would notice a partial request, and positive controls), the host identity over plain and TLS tunnels, and the protocol choice from inside the cage on the Linux engine; the denial log checked for the rules the probes provoke.

**Non-Goals:**
- Method rules keyed on anything but host and path (bodies, query strings, `_method` form fields). The gate decides on the verb and the two header classes above; a request's semantics are the upstream's business, and the README says so.
- Gating CONNECT by method. The verb is inside the tunnel; the inner request is gated.
- A `tjor policy` subcommand that writes restrict or except rules. They are written by hand; `tjor policy add` keeps adding hosts only.
- Changing the default policy's verdicts. The packaged default gains a commented example only.
- Per-broker or per-credential method scopes. The policy is per session; a brokered host is restricted by restricting the host.
- Scanning streamed bodies (#62 stays observe-only and bounded) or answering 403 to a request whose body the proxy will not buffer: a closed connection is the honest answer.
- Keeping HTTP/2 for the sake of HTTP/2-only protocols (gRPC). Stated as a residual; a later change can revisit it with a per-stream answer the proxy does not offer today.

## Decisions

**D1. Schema: `methods.restrict` and `methods.except` as arrays of tables, parsed as strictly as the path rules.**
`[[methods.restrict]]` has exactly `host` (string) and `allow` (list of strings); `[[methods.except]]` has exactly `host`, `path` (strings) and `methods` (list of strings). A method name in the policy must match `^[A-Z][A-Z0-9-]{0,31}$` as written — `"get"` or `"GET "` is a format error, not normalised — because every other parse error in this file is loud rather than forgiving, a policy is written once and reviewed, and every registered HTTP method fits (`VERSION-CONTROL`, `BASELINE-CONTROL`, `UPDATEREDIRECTREF`). An empty `allow = []` is valid and means "no method unless excepted". Any violation makes the whole policy invalid, i.e. deny-everything. `Policy` gains `method_restrict: list[tuple[str, frozenset[str]]]` and `method_except: list[tuple[str, str, frozenset[str]]]`, and a helper `method_restricted(policy, host) -> bool` (any restrict host pattern matches) for the proxy's header guards and the CLI's note.
Alternative: `method = "POST"` on the existing `paths` rules — rejected in the issue: path blocks have no exception mechanism and carve-outs only rescue blocked hosts, so a read-only host with one POST path is not expressible.

**D2. The request method is an exact token of at most 32 characters, validated before any rule; `evaluate(policy, url, method)` has no default.**
The method is compared byte for byte as sent. It must match `re.fullmatch(r"[!#$%&'*+\-.^_`|~0-9A-Za-z]{1,32}", method)` — RFC 9110 `tchar`, ASCII only (a non-ASCII method cannot be a `str` of those characters) — or the verdict is `fail-closed:bad-method`, on every host and whether or not the policy has a `methods` section: a comparison against a restrict list is only sound on a well-formed token, non-token methods are not HTTP, and "deny the malformed thing everywhere" is the simpler rule to state. The 32-character bound is a deliberate limit, not a convenience: the method lands in the denial log, the 403 body and the `x-tjor-rule` header, and twice the longest registered method is room enough; the bound is stated in the proposal, the spec, the README and the CHANGELOG, and a 33-character token is a regression test. No case folding or trimming anywhere: `.upper()` would admit `get` and `GET ` as `GET` while the upstream receives the original, and Python's `upper()` maps `ſ` to `S`, so the addon reads the raw bytes (`flow.request.data.method.decode("ascii")`, a decode failure is `bad-method`) rather than mitmproxy's upper-cased `flow.request.method`. The parameter has no default so a caller that forgets it raises `TypeError` in the first test run instead of silently evaluating a POST as a GET — the one way the gate could be bypassed by construction. The CLI alone defaults to `GET`, for the operator typing a URL, and passes `--method` exactly as typed. Order inside `evaluate`: invalid policy → bad URL → bad method → excessive encoding → stages.
Alternative: validate only when a restrict matches — rejected: it makes the token rule depend on policy content, and a non-token method on an unrestricted host is still not a request tjor should forward. Alternative: no length bound — rejected: an unbounded attacker-chosen string in three operator-facing places buys nothing.

**D3. The gate runs after the mode, on an allowed verdict only.**
`evaluate` computes today's verdict unchanged (stages 1–3, same returns, same rules); if it is a deny, it is returned as is. Only an allow enters the gate: collect every restrict rule whose host pattern matches; none → return the allow; the method listed by all of them → return the allow; otherwise look for an except rule whose host pattern matches, whose `methods` contains the method, and whose path pattern matches every form of the path (`all(...)` over `path_forms`, the allow-side asymmetry) → return the allow; else `Verdict(False, f"method-block:{method}", <host pattern of the first matching restrict that omits the method>)`. The deny-only property is then structural, and the earlier draft's defect (gating before the mode turned a `default-deny` into `method-block:POST`, which contradicted the spec scenario, the property test and the "tjor policy add" hint) cannot recur. Intersection over matching restricts rather than first-match, because the order of `[[…]]` tables in a hand-written file should not decide what a host may do; deny-wins is the fail-closed reading and the README states it. An exception is scoped by its own host and path patterns, not by the restrict it lifts; the spec says so and shows the consequence.

**D4. Two rule prefixes: `method-block:<METHOD>` for the gate, `header-block:<guard>` for the header guards.**
Both follow the existing `stage:detail` convention, so the denial log's three-column format, `tjor denials`, the teardown recap and `_agent_rule` need no format change; a token has no whitespace or control byte, so the attacker-influenced method is safe in the tab-separated log, the 403 body and the `x-tjor-rule` header. The header guards deny with `header-block:upgrade` and `header-block:method-override`. They get their own prefix because their fix is different: a `method-block:` line is widened by a `[[methods.except]]` rule or the restriction's `allow` list, a `header-block:` line only by not restricting the host, and the hints say exactly that. A separate prefix also means a request whose method is literally `upgrade` (denied as `method-block:upgrade`) can never be confused with the guard.
Alternative: a fourth log column with the method for every denial — rejected: it changes a format two readers parse for one stage's benefit. Alternative: `method-block:upgrade` with a lower-case detail — rejected on review: the hint for it would have been wrong, and the collision above is real.

**D5. Call sites: the addon passes the raw method; the CLI gains `--method` and a note; `tjor policy` parses it.**
`decide(url, method)` and `request_verdict(url, host, method)` take the method; the addon passes the ASCII-decoded raw bytes (D2). `tjor_policy.py check --policy P [--method M] [--json] URL`, default `GET`. When the URL's host is method-restricted (`method_restricted`), `check` prints one note after the verdict — the proxy also refuses `Upgrade` and method-override headers on this host, which the preview cannot see — so `tjor policy https://api.example.test/ws --explain` saying ALLOW is not read as a promise. `cmd_policy` in `bin/tjor` parses `--method <M>` and `--method=<M>` (a missing value is a usage error) next to `--explain`, forwards it, and the usage line shows it. The corpus gains a `method` field on every case (explicit, no loader default), method-denial cases, an exception case, an encoded-exception case, a lower-case case, a 32-character token case and a 33-character case; the parity test passes the method to all three call sites and the pytest id becomes `"<METHOD> <url>"`.

**D6. Header guards on restricted hosts live in the addon, beside the IP guard, and have no exception.**
After an allowed verdict, if `tjor_policy.method_restricted(policy, judged_host)`: an `Upgrade` header denies with `header-block:upgrade`; any of `x-http-method-override`, `x-http-method`, `x-method-override` denies with `header-block:method-override`. Deny rather than strip, so the agent and the operator see what happened (`tjor denials`) instead of a silently altered request. No policy rule lifts a guard: a host that legitimately needs WebSocket or override headers is simply not restricted, and the README and the spec say so in those words. Unrestricted hosts are untouched: the identity probes and ordinary WebSocket use on allow-listed hosts keep working. The matcher stays a pure function of (policy, url, method) — headers are not part of the parity corpus — so the CLI cannot preview these two denials beyond the D5 note.
Alternative: an `upgrade = true` field on restrict rules — deferred: no use case yet, and it grows the expression language.

**D7. Enforcement, injection and identity handling move to `requestheaders`; the proxy speaks HTTP/1.1 only; `request` keeps the body scan and a fail-closed check.**
`requestheaders` computes the verdict (D8 identity, D5 method, policy, IP guard, D6 header guards) and stores it in `flow.metadata["tjor_verdict"]`. Allowed: `_apply_identity`, `_apply_broker`, `_apply_gateway` run here, so a streamed request's headers go upstream already rewritten. Denied: `_log_denial`, then one rule on the declared body: `expected_http_body_size(flow.request)` is `0` or a `Content-Length` at or below the threshold → set the 403 as today (mitmproxy consumes the bounded body and answers without an upstream connection); it is `None` (chunked) or above the threshold (`flow.request.stream` is already true) → `flow.kill()`, which closes the connection toward the client before `start_request_stream` can run and before any body byte is read. That rule is exact only when every request declares its body at the headers stage, which HTTP/1.1 guarantees and HTTP/2 does not: an HTTP/2 request without `Content-Length` looks empty to the hook, and if DATA then arrives past the threshold mitmproxy's late switch to streaming hits `start_request_stream` with a response already set, an exception the server logs per frame and never recovers from. So the proxy command gains `--set http2=false` next to `rawtcp=false`: the cage speaks HTTP/1.1 to the agent and upstream, clients that offer both ALPN values fall back transparently, and a client that offers only `h2` fails its handshake. `request` keeps `_scan_request_body` (needs the body) and asserts a verdict was recorded; if none is (a hook path that skipped `requestheaders`), it denies with `fail-closed:hook-error` — defense in depth, not the primary enforcement. The whole hook keeps the existing fail-closed wrapper (set the 403 or kill first, log after); `flow.kill()` raises if the flow is not killable, and the wrapper then falls back to the 403.
Alternatives considered and rejected: keep HTTP/2 and kill every denied HTTP/2 request that declares no `Content-Length` — sound, but it takes the 403 page away from every bodiless denial over HTTP/2 (a GET or DELETE from curl, gh or any Go client), which is the common denial shape, and the reset carries no reason; keep HTTP/2 and answer 403 relying on mitmproxy's refusal to stream an answered flow as the backstop — fail-closed in effect (the raise precedes the upstream connection) but undesigned: an unhandled exception per body frame, a log-spam surface, and a flow left in no defined state. Lowering `stream_large_bodies` or disabling streaming — rejected: the inference paths legitimately carry large bodies, and buffering them in the shared sidecar is the decompression-bomb surface #62 already avoids.

**D8. One host identity: the tunnel target, recorded at CONNECT.**
`http_connect` records, for an allowed CONNECT, the canonical judged host under `flow.client_conn.id` in a module dict (`_tunnel_host`), removed in `client_disconnected`. `requestheaders` derives the judged host: if the client connection has a recorded tunnel host, that host; it must equal `_canon_host(server_conn.sni)` when a TLS server name exists (mitmproxy verifies the upstream certificate against that name, so this is the identity injection already trusts), else `fail-closed:host-mismatch`. Without a tunnel (absolute-form request) the judged host is `flow.request.host`, the URL host from the request line. In both cases, when `flow.request.host_header` is present its host (`url.parse_authority`) must equal the judged host, else `fail-closed:host-mismatch`; an HTTP/1.0 request without `Host` is judged on the URL. With HTTP/2 no longer negotiated there is no `:authority` to consider; `host_header` is the one accessor either way. The URL handed to the matcher is rebuilt from the judged host, `flow.request.scheme`, `flow.request.port` and `flow.request.path`, so `pretty_url` is no longer consulted for a security decision. `_logical_host` becomes this function and keeps serving injection, identity, the IP guard, the #62 scan and the log-volume counter, so one identity feeds every host-scoped decision. A plain-HTTP tunnel (CONNECT to port 80) is judged on the CONNECT target like any other tunnel. A redirect needs nothing: the client follows it with a new request, which arrives at `requestheaders` and is judged like any other; a probe shows a 307 from an excepted path does not carry its POST to a restricted one.
Alternative: SNI only — rejected: a plain tunnel has none, and the tunnel target is what the CONNECT stage already judged.

**D9. `augment_policy` validates first, re-emits from the parsed policy, adds POST exceptions for the gateway's POST inference paths; the launcher writes the session policy only on success.**
The augmentation calls `tjor_policy.parse_policy` on the base policy and raises on `valid=False` with the parser's errors. `ensure_topology` no longer copies the base policy first: with the gateway enabled it runs the augmentation on the base policy file and writes `${TJOR_SESSION_DIR}/policy.toml` from the output only when it succeeds, printing the augmentation's stderr before dying otherwise, so an invalid base policy leaves no session policy behind (the llm-gateway scenario says exactly that); without the gateway it copies as before. The session policy is serialised from the `Policy` dataclass — `mode`, `hosts`, `paths`, `methods` — never from a tolerant re-read, so nothing the parser accepted can be dropped and nothing it rejected can be silently healed. For each inference path that is POST in practice (`/chat/completions`, `/completions`, `/embeddings`, `/messages`, each with and without `/v1`) it adds `[[methods.except]] host = <gateway> path = <path> methods = ["POST"]` (idempotent, like the carve-outs). The gateway host is tjor's own sidecar whose policy the augmentation already defines in full (host block plus carve-outs), so defining its methods there too is consistent; a `host = "*"` restrict written for third-party hosts does not take down the harness's inference path with a confusing `method-block:POST`. The management surface stays denied by the host block, which the gate never lifts. `gateway_test.sh` gains the launcher path: `ensure_topology` in a subshell against a malformed base policy exits non-zero, prints the parser's error, and leaves no session policy.
Alternative: let inference fail closed under a broad restrict — rejected: it is the worst first-hour failure, in tjor's own sidecar, for a rule the operator wrote for other hosts.

**D10. `tjor_policy_edit` distinguishes three shapes of the file.**
Find the `[hosts]` table header (`^\[hosts\]\s*$`, multiline). If absent: append a `[hosts]` table (unchanged). If present: look for `allow = [` within the lines that follow it up to the next table header (`^\[` or `^\[\[`); if found, insert after the bracket; if not, insert an `allow = [ … ]` key right after the `[hosts]` header. The old regex could run into a `[[methods.restrict]]` `allow` list, and stopping at the next header without the third case would append a second `[hosts]` table, which TOML rejects. The parse and semantic re-check stay as they are.

**D11. Proof: unit, parity, conformance with an upstream that would notice.**
Unit tests in `test_policy.py` for every spec scenario, plus a property test: for every corpus URL and each of `GET HEAD POST PUT PATCH DELETE OPTIONS`, the verdict under the fixture policy either equals the verdict under the same policy with both method lists emptied (`dataclasses.replace`), or is a `method-block:*` deny where the stripped verdict allows. Addon tests in `test_addon_guards.py` drive `requestheaders` with fake flows: a chunked denied flow is killed with nothing set as a response, a flow with `stream = True` likewise, a bounded denied flow gets the 403, an allowed streaming flow has its `Authorization` replaced in the hook, the tunnel registry and the mismatch cases (a lying `Host` inside a tunnel, an absolute-form mismatch, a missing `Host`, a tunnel whose SNI differs from its CONNECT target), the two header guards, a `request` without a recorded verdict fails closed.
Conformance fixture. The echo answers every method with `{"method", "headers", "body_len"}`, and records every accepted connection and every request it starts to read — method, path, bytes received so far, complete or not — in a threaded server, serving the record at `GET /_seen` (excluded from the record). A partial request therefore shows up as an incomplete entry and a connection that was never used shows up as a connection, which a per-method counter would miss. It also serves TLS on 8443 from a certificate mounted at `/tls`, and gains the `readonly.test` alias. `cmd_conformance` generates, with the host's `openssl` it already uses for the proxy CA, a self-signed certificate whose SAN lists the echo aliases, into `${TJOR_SESSION_DIR}/conformance-tls/`; writes `${TJOR_SESSION_DIR}/proxy-ca/config.yaml` with `ssl_verify_upstream_trusted_ca` pointing at a copy of that certificate in the same directory (conformance sessions only: no other code path writes that file, and upstream verification itself is unchanged); copies the proxy CA to `${TJOR_SESSION_DIR}/ca.pem` as `tjor run` does; the conformance service mounts it at `/etc/tjor/ca/ca.pem` and the echo service mounts `conformance-tls` at `/tls`. `readonly.test` is allow-listed in `images/conformance/policy.toml`, restricted to `GET`/`HEAD`, with `POST` excepted on `/search`; the parity fixture carries the same rules so the corpus and the probes read one policy shape.
Probes. Fifteen, each asserting the exact `x-tjor-rule` where a 403 is the expected answer: (1) a POST to `/items` on `readonly.test` is denied `method-block:POST`; (2) a GET to `/items` returns the echo's 200; (3) a POST to `/search` returns 200; (4) a POST to `/%73earch` is denied `method-block:POST`; (5) a POST to `/search` that the echo answers with a 307 to `/items` is followed by the probe and the second POST is denied `method-block:POST`; (6) inside a plain CONNECT tunnel to `readonly.test:8080` a GET with a matching `Host` returns 200 and a POST is denied `method-block:POST`; (7) the same inside a TLS tunnel to `readonly.test:8443` (`http.client.HTTPSConnection` with `set_tunnel`, the mounted proxy CA), so the SNI path is live; (8) a GET with `Upgrade: websocket` is denied `header-block:upgrade`; (9) a GET with `X-HTTP-Method-Override: DELETE` is denied `header-block:method-override`; (10) inside a plain tunnel to `echo-noinject.tjor-test:8080` a GET with `Host: readonly.test` is denied `fail-closed:host-mismatch`; (11) an absolute-form GET to the echo with `Host: readonly.test:8080` is denied `fail-closed:host-mismatch`; (12) a TLS handshake through a tunnel that offers `h2` before `http/1.1` negotiates `http/1.1`, and the request inside it returns 200; (13) with a positive control first — a 2 MiB `Content-Length` POST to `/search` arrives complete with `body_len` 2 MiB — a 2 MiB `Content-Length` POST to `/items` ends in a closed connection and `/_seen` shows no new connection and no new request; (14) the same with chunked bodies, the denied one to `/phone-home/x` (path-blocked); (15) a 2 MiB POST to `echo-broker.tjor-test` with a forged `x-agent-*` header arrives complete with the real token and without the header. Probes 13 and 14 fail if the positive control does not arrive complete, so an unrelated connection failure cannot pass as a denial. For every denial a probe provokes it prints `expect-denial\t<host>\t<rule>`; after the run `cmd_conformance` checks each pair against `${TJOR_SESSION_DIR}/denials.log` before the EXIT trap removes it, prints `denials: N/N expected rules recorded`, and fails the run when one is missing — that is how the killed requests (13, 14) are shown to have been denied by the right rule, since a closed connection carries none. The registry gains the fifteen names (fourteen under `egress-policy`, the last under `credential-broker`) and the matrix is regenerated; CI's `conformance` job reports 34 probes.

**D12. Docs state the residuals; an ADR records the enforcement point, the protocol choice and the identity.**

## Risks / Trade-offs

- [An operator restricts a host the harness writes to, e.g. the LLM endpoint] → loud and specific: every request fails with `method-block:POST`, `tjor denials` shows it with the exception hint, `tjor policy <url> --method POST` previews it; the gateway host is excepted by construction; the README example restricts an API host, never a harness endpoint.
- [The gate is mistaken for a semantic read-only guarantee] → the README, the spec's limits requirement and the slide say the gate sees the verb and two header classes only, name GraphQL as the case where a POST exception admits writes, and the exception example uses a search endpoint because that is where POST-as-read is common.
- [A denied large upload now ends in a closed connection, not a 403] → the denial log records it with its rule; the README says a closed connection on a large or chunked request means a denial and points at `tjor denials`.
- [HTTP/2-only clients stop working inside the cage] → gRPC and similar protocols; stated in the README, the spec's limits, the CHANGELOG and the ADR; a client offering only `h2` fails its handshake rather than falling into an unenforced path; every ordinary CLI (curl, gh, git, Go, Node, Python) offers HTTP/1.1 too.
- [A client whose `Host` legitimately differs from its connection host] → none known (curl, git, gh, Python, Node, Go all send the URL host); the denial names `host-mismatch` so it is diagnosable, and the alternative is a bypass.
- [A future call site evaluates without a method] → impossible by signature; the parity suite additionally fails if any call site disagrees on a method case.
- [Overlapping restricts or wide exceptions surprise an operator] → stated in the README and the spec (intersection; exception scope); `tjor policy --method` shows which pattern decided.
- [The Python API signature change] → in-repo callers only; all updated in the same change.
- [Moving injection to `requestheaders` changes the hook that existing tests drive] → the tests are updated with the hook; the conformance suite proves the end-to-end behaviour on small, large and chunked requests, over plain and TLS tunnels.
- [The conformance topology adds a trust anchor to the proxy] → a conformance-only file in a temporary session directory, pointing at a certificate for the test aliases alone; verification logic is untouched and `tjor run` never writes it.

## Migration Plan

Additive for policies: a file without a `methods` section is unaffected; `tjor policy <url>` without `--method` evaluates `GET`. Behaviour changes at the proxy are denials of requests no legitimate client sends (host mismatch, non-token method), denials of requests that were already denied but delivered (streamed), and the loss of HTTP/2 negotiation, which every ordinary client absorbs by falling back. No data or config migrates. Rollback is reverting the change; a policy file carrying a `methods` section would then fail to parse (unknown top-level key) and deny everything — the loud direction.
