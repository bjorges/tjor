# Design

## Context

See proposal.md — Why. What exists today, verified in the code and in the pinned mitmproxy (12.1.2, `config/tjor.toml`) source, and shapes the approach:

- `python/tjor_policy.py` is the single matcher (charter L4). `parse_policy` is strict: `_TOP_KEYS = {mode, hosts, paths}`, a rule entry has exactly `{host, path}`, and any unknown key or wrong type makes the whole policy `valid=False`, which `evaluate` and `evaluate_connect` turn into deny-everything. `evaluate(policy, url)` runs: invalid policy → bad URL → excessive encoding → host blocklist, where a matching block pattern either returns an all-forms carve-out allow or a `host-block` deny → any-form path blocks → default mode. That precedence is spec'd and tested.
- `Verdict.rule` names the deciding stage and carries detail after a colon where there is detail: `fail-closed:bad-url`, `ip-guard:<why>`, `connect-defer:carveout`. The 403 body and the `x-tjor-rule` header show the rule; the session denial log is `host\trule\ttime`; `tjor denials` prints it as is and the teardown recap reads only the host column. Both end with "allow what you need with: tjor policy add <host>" (`bin/tjor` cmd_denials, the teardown recap).
- Three call sites: `proxy/addon.py` (`decide(url)` from `request_verdict(url, host)`, called by the `request` hook with `flow.request.pretty_url`; `decide_connect(host)` from `http_connect`), the `tjor_policy.py check` CLI behind `tjor policy <url> [--explain]` (whose argument loop strips only `--explain`, so `--method POST` would be read as the URL), and the module API used by tests, `tjor_gateway` and `tjor_policy_edit`. `evaluate(` is called 19 times in `test_policy.py`, 9 in `test_gateway.py`, 4 in `test_config_ergonomics.py`; `test_addon_guards.py` calls `request_verdict` with two arguments at five places and stubs `decide` as `lambda url:` once. `python/tests/test_parity.py` runs `python/tests/fixtures/corpus.json` (21 URL cases, no method) against all three.
- The addon's `request` hook does everything: verdict, 403, then for an allowed request identity handling, broker and gateway injection, and the #62 body scan. mitmproxy fires `request` once the whole body has been read ("If request streaming is active, this event fires after the entire body has been streamed", `proxy/layers/http/_hooks.py`). In `state_wait_for_request_headers`, `check_body_size` runs *before* the `requestheaders` hook and sets `flow.request.stream = True` when the declared body exceeds `stream_large_bodies` (1 MiB in compose.yaml); right after the hook, `start_request_stream` opens the upstream connection and sends the request headers, then streams the body, and only then fires `request`. A chunked body has no declared size, so it is buffered and streaming starts, headers first, once the buffer passes the threshold. `start_request_stream` raises `NotImplementedError` if a response has been set on a streaming flow. `requestheaders` therefore is the last point at which nothing has gone upstream, and the only hook at which a 403 or a kill (`flow.kill()` → `check_killed` → the stream is closed toward the client) can prevent delivery for every request shape.
- `flow.request.method` is mitmproxy's `.upper()` of the raw method bytes (`http.py`); the raw bytes are `flow.request.data.method` and are what goes upstream. mitmproxy's HTTP/1 request-line reader splits on whitespace and validates only the HTTP version, so a non-token method reaches the addon unchanged. HTTP/2's `:method` is read the same way.
- `flow.request.pretty_url` builds its host from `Host` (`:authority`), which mitmproxy's own docstring calls spoofable in adversarial settings. Inside a CONNECT tunnel the inner HTTP layer runs in transparent mode, so `flow.request.host` is the tunnel's server address (the #41 pinned IP after `server_connect`) and the verified TLS server name is `flow.server_conn.sni`; `_logical_host` already keys injection on that SNI (ADR 0007) and falls back to `pretty_host`. For a request sent directly to the proxy (absolute-form, plain HTTP) `flow.request.host` is the URL's host from the request line; mitmproxy clears `authority` on HTTP/1 before the hooks run, so `first_line_format` cannot tell the two shapes apart, but `flow.client_conn` is the same object (with a stable `id`) for a CONNECT flow and every flow inside its tunnel.
- `python/tjor_gateway.py` `augment_policy` re-reads the base policy with `tomllib` and a tolerant shape (malformed rules and unknown keys are skipped), then writes `mode`, `hosts` and the two `paths` lists. The launcher validates only the augmented output (`bin/tjor` ensure_topology). A base policy with `allows = [...]` under `[[methods.restrict]]`, or `[[methods.restirct]]`, would come out valid and unrestricted. The gateway's inference paths are carved in as `paths.allow` on the gateway host, which sits in `hosts.block`; four of them are POST-only in practice (`/chat/completions`, `/completions`, `/embeddings`, `/messages`, with and without `/v1`), `/models` and the health paths are GET.
- `python/tjor_policy_edit.py` inserts new hosts after the first `allow = [` that follows `[hosts]`, anywhere in the file, and otherwise appends a new `[hosts]` table; a second `[hosts]` table is a TOML error, and a restrict rule has an `allow` list of its own.
- The conformance suite runs `images/conformance/probes.py` inside the cage against `images/conformance/policy.toml`; `via_proxy` sends absolute-form GETs; `is_policy_deny` is "403 with `x-tjor-policy: deny`" and does not look at the rule. The egress-side echo fixture (`images/conformance/echo.py`) answers GET only and reflects headers; it is reachable through the proxy under compose aliases on the egress network. Every probe name is registered in `python/gen_boundary_matrix.py`; `tests/doc_consistency.sh` fails when the registry and the probe sources disagree or `docs/boundary-matrix.md` is stale.
- `python/gen_corefile.py` derives DNS zones from `host_allow` only; the broker and identity modules use `host_matches` only. None of them evaluates a request.

## Goals / Non-Goals

**Goals:**
- A restrict/except pair in the policy that can only narrow, with the same encoding asymmetry as the path rules, evaluated by the one matcher and proven at all three call sites.
- No silent path by which a restriction is lost: not by a call site that forgets the method, not by the gateway augmentation, not by `tjor policy add`, not by a header that changes what the verb means (`Upgrade`, method override), not by a body that is streamed before the verdict, not by a `Host` header that names another host.
- The refused method visible wherever a denial is visible, with a hint that leads to the right fix.
- Conformance probes that prove the gate, the header guards, the enforcement point and the host identity from inside the cage on the Linux engine.

**Non-Goals:**
- Method rules keyed on anything but host and path (bodies, query strings, `_method` form fields). The gate decides on the verb and the two header classes above; a request's semantics are the upstream's business, and the README says so.
- Gating CONNECT by method. The verb is inside the tunnel; the inner request is gated.
- A `tjor policy` subcommand that writes restrict or except rules. They are written by hand; `tjor policy add` keeps adding hosts only.
- Changing the default policy's verdicts. The packaged default gains a commented example only.
- Per-broker or per-credential method scopes. The policy is per session; a brokered host is restricted by restricting the host.
- Scanning streamed bodies (#62 stays observe-only and bounded) or answering 403 to a streamed denied request: a closed stream is the honest answer when the proxy will not buffer the body.

## Decisions

**D1. Schema: `methods.restrict` and `methods.except` as arrays of tables, parsed as strictly as the path rules.**
`[[methods.restrict]]` has exactly `host` (string) and `allow` (list of strings); `[[methods.except]]` has exactly `host`, `path` (strings) and `methods` (list of strings). A method name in the policy must match `^[A-Z][A-Z0-9-]{0,31}$` as written — `"get"` or `"GET "` is a format error, not normalised — because every other parse error in this file is loud rather than forgiving, a policy is written once and reviewed, and every registered HTTP method fits (`VERSION-CONTROL`, `BASELINE-CONTROL`, `UPDATEREDIRECTREF`). An empty `allow = []` is valid and means "no method unless excepted". Any violation makes the whole policy invalid, i.e. deny-everything. `Policy` gains `method_restrict: list[tuple[str, frozenset[str]]]` and `method_except: list[tuple[str, str, frozenset[str]]]`, and a helper `method_restricted(policy, host) -> bool` (any restrict host pattern matches) for the proxy's header guards.
Alternative: `method = "POST"` on the existing `paths` rules — rejected in the issue: path blocks have no exception mechanism and carve-outs only rescue blocked hosts, so a read-only host with one POST path is not expressible.

**D2. The request method is an exact token, validated before any rule; `evaluate(policy, url, method)` has no default.**
The method is compared byte for byte as sent. It must match `re.fullmatch(r"[!#$%&'*+\-.^_`|~0-9A-Za-z]{1,32}", method)` — RFC 9110 `tchar`, ASCII only (a non-ASCII method cannot be a `str` of those characters), length-bounded defensively — or the verdict is `fail-closed:bad-method`, on every host and whether or not the policy has a `methods` section: a comparison against a restrict list is only sound on a well-formed token, non-token methods are not HTTP, and "deny the malformed thing everywhere" is the simpler rule to state. No case folding or trimming anywhere: `.upper()` would admit `get` and `GET ` as `GET` while the upstream receives the original, and Python's `upper()` maps `ſ` to `S`, so the addon reads the raw bytes (`flow.request.data.method.decode("ascii")`, a decode failure is `bad-method`) rather than mitmproxy's upper-cased `flow.request.method`. The parameter has no default so a caller that forgets it raises `TypeError` in the first test run instead of silently evaluating a POST as a GET — the one way the gate could be bypassed by construction. The CLI alone defaults to `GET`, for the operator typing a URL, and passes `--method` exactly as typed. Order inside `evaluate`: invalid policy → bad URL → bad method → excessive encoding → stages.
Alternative: validate only when a restrict matches — rejected: it makes the token rule depend on policy content, and a non-token method on an unrestricted host is still not a request tjor should forward.

**D3. The gate runs after the mode, on an allowed verdict only.**
`evaluate` computes today's verdict unchanged (stages 1–3, same returns, same rules); if it is a deny, it is returned as is. Only an allow enters the gate: collect every restrict rule whose host pattern matches; none → return the allow; the method listed by all of them → return the allow; otherwise look for an except rule whose host pattern matches, whose `methods` contains the method, and whose path pattern matches every form of the path (`all(...)` over `path_forms`, the allow-side asymmetry) → return the allow; else `Verdict(False, f"method-block:{method}", <host pattern of the first matching restrict that omits the method>)`. The deny-only property is then structural, and the earlier draft's defect (gating before the mode turned a `default-deny` into `method-block:POST`, which contradicted the spec scenario, the property test and the "tjor policy add" hint) cannot recur. Intersection over matching restricts rather than first-match, because the order of `[[…]]` tables in a hand-written file should not decide what a host may do; deny-wins is the fail-closed reading and the README states it. An exception is scoped by its own host and path patterns, not by the restrict it lifts; the spec says so and shows the consequence.

**D4. The rule string carries the method: `method-block:<METHOD>`; the header guards reuse the prefix.**
This follows the existing `stage:detail` convention, so the denial log's three-column format, `tjor denials`, the teardown recap and `_agent_rule` need no format change; a token has no whitespace or control byte, so the attacker-influenced method is safe in the tab-separated log, the 403 body and the `x-tjor-rule` header. The header guards deny with `method-block:upgrade` and `method-block:override-header` (lower-case detail, so they cannot collide with a method name, which starts with an upper-case letter in any policy). `tjor denials` and the recap recognise the `method-block:` prefix to print the exception hint.
Alternative: a fourth log column with the method for every denial — rejected: it changes a format two readers parse for one stage's benefit.

**D5. Call sites: the addon passes the raw method; the CLI gains `--method`; `tjor policy` parses it.**
`decide(url, method)` and `request_verdict(url, host, method)` take the method; the addon passes the ASCII-decoded raw bytes (D2). `tjor_policy.py check --policy P [--method M] [--json] URL`, default `GET`. `cmd_policy` in `bin/tjor` parses `--method <M>` and `--method=<M>` (a missing value is a usage error) next to `--explain`, forwards it, and the usage line shows it. The corpus gains a `method` field on every case (explicit, no loader default), method-denial cases, an exception case, an encoded-exception case, a lower-case case and a non-token case; the parity test passes the method to all three call sites and the pytest id becomes `"<METHOD> <url>"`.

**D6. Header guards on restricted hosts live in the addon, beside the IP guard.**
After an allowed verdict, if `tjor_policy.method_restricted(policy, judged_host)`: an `Upgrade` header denies with `method-block:upgrade`; any of `x-http-method-override`, `x-http-method`, `x-method-override` denies with `method-block:override-header`. Deny rather than strip, so the agent and the operator see what happened (`tjor denials`) instead of a silently altered request. Unrestricted hosts are untouched: the identity probes and ordinary WebSocket use on allow-listed hosts keep working. The matcher stays a pure function of (policy, url, method) — headers are not part of the parity corpus — so the CLI cannot preview these two denials; the README says so.
Alternative: an `upgrade = true` field on restrict rules — deferred: no use case yet, and it grows the expression language.

**D7. Enforcement, injection and identity handling move to `requestheaders`; `request` keeps the body scan and a fail-closed check.**
`requestheaders` computes the verdict (D8 identity, D5 method, policy, IP guard, D6 header guards) and stores it in `flow.metadata["tjor_verdict"]`. Allowed: `_apply_identity`, `_apply_broker`, `_apply_gateway` run here, so a streamed request's headers go upstream already rewritten. Denied: `_log_denial`, then if `flow.request.stream` is false and `expected_http_body_size(flow.request)` is a known size (0 or a Content-Length at or below the threshold) set the 403 response as today — mitmproxy consumes the bounded body and answers without an upstream connection; otherwise (`stream` already true, or a chunked body of unknown size that would flip to streaming past the threshold and hit `NotImplementedError` with a response set) `flow.kill()`, which closes the stream toward the client before `start_request_stream` can run. `request` keeps `_scan_request_body` (needs the body) and asserts a verdict was recorded; if none is (a hook path that skipped `requestheaders`), it denies with `fail-closed:hook-error` — defense in depth, not the primary enforcement. The whole hook keeps the existing fail-closed wrapper (set the 403 or kill first, log after). Note for the fail-closed wrapper: `flow.kill()` raises if the flow is not killable; the wrapper falls back to the 403.
Alternative: lower `stream_large_bodies` or disable streaming — rejected: the inference paths legitimately carry large bodies, and buffering them in the shared sidecar is the decompression-bomb surface #62 already avoids.

**D8. One host identity: the tunnel target, recorded at CONNECT.**
`http_connect` records, for an allowed CONNECT, the canonical judged host under `flow.client_conn.id` in a module dict (`_tunnel_host`), removed in `client_disconnected`. `requestheaders` derives the judged host: if the client connection has a recorded tunnel host, that host; it must equal `_canon_host(server_conn.sni)` when a TLS server name exists (mitmproxy verifies the upstream certificate against that name, so this is the identity injection already trusts), else `fail-closed:host-mismatch`. Without a tunnel (absolute-form request) the judged host is `flow.request.host`, the URL host from the request line. In both cases, when `flow.request.host_header` is present its host (`url.parse_authority`) must equal the judged host, else `fail-closed:host-mismatch`; an HTTP/1.0 request without `Host` is judged on the URL. The URL handed to the matcher is rebuilt from the judged host, `flow.request.scheme`, `flow.request.port` and `flow.request.path`, so `pretty_url` is no longer consulted for a security decision. `_logical_host` becomes this function and keeps serving injection, identity, the IP guard, the #62 scan and the log-volume counter, so one identity feeds every host-scoped decision. A plain-HTTP tunnel (CONNECT to port 80) is judged on the CONNECT target like any other tunnel.
Alternative: SNI only — rejected: a plain tunnel has none, and the tunnel target is what the CONNECT stage already judged.

**D9. `augment_policy` validates first, re-emits from the parsed policy, and adds POST exceptions for the gateway's POST inference paths.**
The augmentation calls `tjor_policy.parse_policy` on the base policy and raises on `valid=False` with the parser's errors; `ensure_topology` already dies when the augmentation fails and now prints those errors. The session policy is serialised from the `Policy` dataclass — `mode`, `hosts`, `paths`, `methods` — never from a tolerant re-read, so nothing the parser accepted can be dropped and nothing it rejected can be silently healed. For each inference path that is POST in practice (`/chat/completions`, `/completions`, `/embeddings`, `/messages`, each with and without `/v1`) it adds `[[methods.except]] host = <gateway> path = <path> methods = ["POST"]` (idempotent, like the carve-outs). The gateway host is tjor's own sidecar whose policy the augmentation already defines in full (host block plus carve-outs), so defining its methods there too is consistent; a `host = "*"` restrict written for third-party hosts does not take down the harness's inference path with a confusing `method-block:POST`. The management surface stays denied by the host block, which the gate never lifts.
Alternative: let inference fail closed under a broad restrict — rejected: it is the worst first-hour failure, in tjor's own sidecar, for a rule the operator wrote for other hosts.

**D10. `tjor_policy_edit` distinguishes three shapes of the file.**
Find the `[hosts]` table header (`^\[hosts\]\s*$`, multiline). If absent: append a `[hosts]` table (unchanged). If present: look for `allow = [` within the lines that follow it up to the next table header (`^\[` or `^\[\[`); if found, insert after the bracket; if not, insert an `allow = [ … ]` key right after the `[hosts]` header. The old regex could run into a `[[methods.restrict]]` `allow` list, and stopping at the next header without the third case would append a second `[hosts]` table, which TOML rejects. The parse and semantic re-check stay as they are.

**D11. Proof: unit, parity, conformance.**
Unit tests in `test_policy.py` for every spec scenario, plus a property test: for every corpus URL and each of `GET HEAD POST PUT PATCH DELETE OPTIONS`, the verdict under the fixture policy either equals the verdict under the same policy with both method lists emptied (`dataclasses.replace`), or is a `method-block:*` deny where the stripped verdict allows. Addon tests in `test_addon_guards.py` drive `requestheaders` with fake flows: a streaming flow is killed and nothing is set as a response, a bounded flow gets the 403, an allowed streaming flow has its `Authorization` replaced in the hook, the tunnel registry and the mismatch cases, the two header guards, a `request` without a recorded verdict fails closed. Conformance: the echo fixture answers every method (reflecting method, headers and body length), keeps a per-method request counter served at `GET /_seen`, and gains a `readonly.test` alias on the egress network; `readonly.test` is allow-listed, restricted to `GET`/`HEAD`, with `POST` excepted on `/search`. Ten probes, all with exact rule assertions: a POST to `/items` is denied with `x-tjor-rule: method-block:POST`; a GET to `/items` returns the echo's 200; a POST to `/search` returns 200; a POST to `/%73earch` is denied with `method-block:POST`; a GET with `Upgrade: websocket` is denied with `method-block:upgrade`; a GET with `X-HTTP-Method-Override: DELETE` is denied with `method-block:override-header`; a 2 MiB POST to `/phone-home/x` (path-blocked) and a chunked 2 MiB POST to `/items` both end in a denial (403 or a closed connection) and leave the echo's counter unchanged; an absolute-form GET to the echo with `Host: readonly.test` is denied with `fail-closed:host-mismatch`; a 2 MiB POST to the broker echo host arrives with the real token and without a forged `x-agent-*` header. The registry gains the ten names (nine under `egress-policy`, the last under `credential-broker`) and the matrix is regenerated; the conformance policy and the parity fixture carry the same method rules so the corpus and the probes read one policy shape.

**D12. Docs state the residual; an ADR records the enforcement point and the identity.**
README "Egress policy": the read-only API example (`GET`/`HEAD`, `POST` excepted on `/rest/api/2/search`), the read-only git example (`POST` excepted on `/*/git-upload-pack`, because fetch and clone POST there), the deny-only property, intersection of overlapping restricts, exception scope, the header guards and that `tjor policy` cannot preview them, and the limits: the gate sees the verb, not what the request does; an exception is as wide as its path pattern and `*` spans `/`; CONNECT is decided on the host, each inner request on its method. README "LLM gateway": method rules survive augmentation, the gateway's POST paths are excepted, an invalid policy fails the launch. `config/policy.toml`: the API example, commented out. `docs/decisions/0012-headers-stage-enforcement-and-host-identity.md`: why the verdict is bound to the connection's host and why every security-relevant hook action happens before the body, with the mitmproxy facts above, so neither is undone by a later refactor. CHANGELOG under `[Unreleased]`: Added (the gate, `--method`, the probes), Changed (augmentation, `tjor policy add` anchoring, the API signature, host-mismatch and bad-method denials), Fixed (streamed requests escaped path blocks and received the placeholder credential; a `Host` header could steer a verdict). Slides: "A policy that can be bent" gets the method gate in its precedence line and a bullet with the residual; "Policy has to see the request" says the method as well as the path is decided after TLS termination and before any byte goes upstream; the ergonomics slide shows `--method`; the gateway slide says the inference paths survive method restrictions; all five pins updated.

## Risks / Trade-offs

- [An operator restricts a host the harness writes to, e.g. the LLM endpoint] → loud and specific: every request fails with `method-block:POST`, `tjor denials` shows it with the exception hint, `tjor policy <url> --method POST` previews it; the gateway host is excepted by construction; the README example restricts an API host, never a harness endpoint.
- [The gate is mistaken for a semantic read-only guarantee] → the README, the spec's limits requirement and the slide say the gate sees the verb and two header classes only; the exception example uses a search endpoint because that is where POST-as-read is common.
- [A denied large upload now ends in a closed connection, not a 403] → the denial log records it with its rule; the README says a closed connection on a large or chunked request means a denial and points at `tjor denials`.
- [A client whose `Host` legitimately differs from its connection host] → none known (curl, git, gh, Python, Node, Go all send the URL host); the denial names `host-mismatch` so it is diagnosable, and the alternative is a bypass.
- [A future call site evaluates without a method] → impossible by signature; the parity suite additionally fails if any call site disagrees on a method case.
- [Overlapping restricts or wide exceptions surprise an operator] → stated in the README and the spec (intersection; exception scope); `tjor policy --method` shows which pattern decided.
- [The Python API signature change] → in-repo callers only; all updated in the same change.
- [Moving injection to `requestheaders` changes the hook that existing tests drive] → the tests are updated with the hook; the conformance suite proves the end-to-end behaviour on both small and streamed requests.

## Migration Plan

Additive for policies: a file without a `methods` section is unaffected; `tjor policy <url>` without `--method` evaluates `GET`. Behaviour changes at the proxy are all denials of requests no legitimate client sends (host mismatch, non-token method) or of requests that were already denied but delivered (streamed). No data or config migrates. Rollback is reverting the change; a policy file carrying a `methods` section would then fail to parse (unknown top-level key) and deny everything — the loud direction.
