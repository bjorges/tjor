# Design

## Context

See proposal.md — Why. What exists today, verified in the code and in the pinned mitmproxy (12.1.2, `config/tjor.toml`) source, and shapes the approach:

- `python/tjor_policy.py` is the single matcher (charter L4). `parse_policy` is strict: `_TOP_KEYS = {mode, hosts, paths}`, a rule entry has exactly `{host, path}`, and any unknown key or wrong type makes the whole policy `valid=False`, which `evaluate` and `evaluate_connect` turn into deny-everything. `evaluate(policy, url)` runs: invalid policy → bad URL → excessive encoding → host blocklist, where a matching block pattern either returns an all-forms carve-out allow or a `host-block` deny → any-form path blocks → default mode. That precedence is spec'd and tested.
- `Verdict.rule` names the deciding stage and carries detail after a colon where there is detail: `fail-closed:bad-url`, `ip-guard:<why>`, `connect-defer:carveout`. The 403 body and the `x-tjor-rule` header show the rule; the session denial log is `host\trule\ttime`; `tjor denials` prints it as is and the teardown recap reads only the host column. Both end with "allow what you need with: tjor policy add <host>" (`bin/tjor` cmd_denials, the teardown recap).
- Three call sites: `proxy/addon.py` (`decide(url)` from `request_verdict(url, host)`, which after PR #87 runs in the `requestheaders` hook on the judged host; `decide_connect(host)` from `http_connect`), the `tjor_policy.py check` CLI behind `tjor policy <url> [--explain]` (whose argument loop strips only `--explain`, so `--method POST` would be read as the URL; `--json` prints a JSON object), and the module API used by tests, `tjor_gateway` and `tjor_policy_edit`. `evaluate(` is called 19 times in `test_policy.py`, 9 in `test_gateway.py`, 4 in `test_config_ergonomics.py`; `test_addon_guards.py` calls `request_verdict` with two arguments at five places and stubs `decide` as `lambda url:` once. `python/tests/test_parity.py` runs `python/tests/fixtures/corpus.json` (21 URL cases, no method) against all three.
- `flow.request.method` is mitmproxy's `.upper()` of the raw method bytes (`http.py`); the raw bytes are `flow.request.data.method` and are what goes upstream. mitmproxy's HTTP/1 request-line reader splits on whitespace (so request-line whitespace is normalised before any addon sees it) and validates the framing when `validate_inbound_headers` is on, which PR #87 makes explicit.
- Protocol switching in mitmproxy: a `101` response becomes a WebSocket channel only when the response says `Upgrade: websocket` *and the request* carried `Sec-WebSocket-Version: 13` — the request's own `Upgrade` header is not consulted; any other `101` is forwarded to the client and, with `rawtcp=false`, the connection is then closed ("no protocol is enabled to upgrade to"). The `responseheaders` hook runs before the response is sent to the client.
- `python/tjor_gateway.py` `augment_policy` re-reads the base policy with `tomllib` and a tolerant shape (malformed rules and unknown keys are skipped), then writes `mode`, `hosts` and the two `paths` lists. `bin/tjor` `ensure_topology` copies the base policy to `${TJOR_SESSION_DIR}/policy.toml` first, augments that copy, and validates only the augmented output. A session directory is deterministic per workspace and session name and is reused by a relaunch; `ensure_topology` recreates the proxy only when the config hash changed. `tests/integration/gateway_test.sh` sources `bin/tjor`, reproduces the augmentation by calling the Python CLI (not `ensure_topology`), and itself writes `${TJOR_SESSION_DIR}/policy.toml`. A base policy with `allows = [...]` under `[[methods.restrict]]`, or `[[methods.restirct]]`, would come out valid and unrestricted. The gateway's inference paths are carved in as `paths.allow` on the gateway host, which sits in `hosts.block`; four of them are POST-only in practice (`/chat/completions`, `/completions`, `/embeddings`, `/messages`, with and without `/v1`), `/models` and the health paths are GET.
- `python/tjor_policy_edit.py` inserts new hosts after the first `allow = [` that follows `[hosts]`, anywhere in the file, and otherwise appends a new `[hosts]` table; a second `[hosts]` table is a TOML error, and a restrict rule has an `allow` list of its own.
- Conformance after PR #87: the echo fixture answers every method, records connections and requests at `/_seen`, serves TLS on 8443 from a conformance-only certificate the proxy trusts, carries the `readonly.test` alias, and `images/conformance/policy.toml` allow-lists `readonly.test`; the probe file has plain-tunnel and TLS-tunnel helpers, `expect_denial`, and `cmd_conformance` checks the denial log by count; 30 probes. `is_policy_deny` is "403 with `x-tjor-policy: deny`" and does not look at the rule. Every probe name is registered in `python/gen_boundary_matrix.py`.
- `python/gen_corefile.py` derives DNS zones from `host_allow` only; the broker and identity modules use `host_matches` only. None of them evaluates a request.

## Goals / Non-Goals

**Goals:**
- A restrict/except pair in the policy that can only narrow, with the same encoding asymmetry as the path rules, evaluated by the one matcher and proven at all three call sites.
- No silent path by which a restriction is lost: not by a call site that forgets the method, not by the gateway augmentation, not by `tjor policy add`, not by a header or a response that changes what the verb means.
- The refused method or guard visible wherever a denial is visible, each with the hint that leads to its fix.
- Conformance probes that prove the gate, the redirect case, both tunnel shapes and the three header guards from inside the cage on the Linux engine.

**Non-Goals:**
- Method rules keyed on anything but host and path (bodies, query strings, `_method` form fields). The gate decides on the verb and the header classes above; a request's semantics are the upstream's business, and the README says so.
- Gating CONNECT by method. The verb is inside the tunnel; the inner request is gated.
- A `tjor policy` subcommand that writes restrict or except rules. They are written by hand; `tjor policy add` keeps adding hosts only.
- Changing the default policy's verdicts. The packaged default gains a commented example only.
- Per-broker or per-credential method scopes. The policy is per session; a brokered host is restricted by restricting the host.
- The enforcement point, the host identity, the transport and the recording fixture: PR #87.

## Decisions

**D1. Schema: `methods.restrict` and `methods.except` as arrays of tables, parsed as strictly as the path rules.**
`[[methods.restrict]]` has exactly `host` (string) and `allow` (list of strings); `[[methods.except]]` has exactly `host`, `path` (strings) and `methods` (list of strings). A method name in the policy must match `^[A-Z][A-Z0-9-]{0,31}$` as written — `"get"` or `"GET "` is a format error, not normalised — because every other parse error in this file is loud rather than forgiving, a policy is written once and reviewed, and every registered HTTP method fits (`VERSION-CONTROL`, `BASELINE-CONTROL`, `UPDATEREDIRECTREF`). An empty `allow = []` is valid and means "no method unless excepted". Any violation makes the whole policy invalid, i.e. deny-everything. `Policy` gains `method_restrict: list[tuple[str, frozenset[str]]]` and `method_except: list[tuple[str, str, frozenset[str]]]`, and a helper `method_restricted(policy, host) -> bool` (any restrict host pattern matches) for the proxy's header guards and the CLI's note.
Alternative: `method = "POST"` on the existing `paths` rules — rejected in the issue: path blocks have no exception mechanism and carve-outs only rescue blocked hosts, so a read-only host with one POST path is not expressible.

**D2. The request method is an exact token of at most 32 characters, validated before any rule; `evaluate(policy, url, method)` has no default.**
The method is compared byte for byte as sent. It must match `re.fullmatch(r"[!#$%&'*+\-.^_`|~0-9A-Za-z]{1,32}", method)` — RFC 9110 `tchar`, ASCII only — or the verdict is `fail-closed:bad-method`, on every host and whether or not the policy has a `methods` section: a comparison against a restrict list is only sound on a well-formed token, non-token methods are not HTTP, and "deny the malformed thing everywhere" is the simpler rule to state. The 32-character bound is a deliberate limit: the method lands in the denial log, the 403 body and the `x-tjor-rule` header, twice the longest registered method is room enough, and the bound is stated in the proposal, the spec, the README and the CHANGELOG with a 33-character regression test. No case folding or trimming anywhere: `.upper()` would admit `get` and `GET ` as `GET` while the upstream receives the original, and Python's `upper()` maps `ſ` to `S`, so the addon reads the raw bytes (`flow.request.data.method.decode("ascii")`, a decode failure is `bad-method`) rather than mitmproxy's upper-cased `flow.request.method`. mitmproxy normalises request-line whitespace before the addon runs, so this is validation of the parsed method, with the parser's own validation (`validate_inbound_headers`, explicit since PR #87) as the precondition. The parameter has no default so a caller that forgets it raises `TypeError` in the first test run instead of silently evaluating a POST as a GET. The CLI alone defaults to `GET`, for the operator typing a URL, and passes `--method` exactly as typed. Order inside `evaluate`: invalid policy → bad URL → bad method → excessive encoding → stages.
Alternative: validate only when a restrict matches — rejected: it makes the token rule depend on policy content. Alternative: no length bound — rejected: an unbounded attacker-chosen string in three operator-facing places buys nothing.

**D3. The gate runs after the mode, on an allowed verdict only.**
`evaluate` computes today's verdict unchanged (stages 1–3, same returns, same rules); if it is a deny, it is returned as is. Only an allow enters the gate: collect every restrict rule whose host pattern matches; none → return the allow; the method listed by all of them → return the allow; otherwise look for an except rule whose host pattern matches, whose `methods` contains the method, and whose path pattern matches every form of the path (`all(...)` over `path_forms`, the allow-side asymmetry) → return the allow; else `Verdict(False, f"method-block:{method}", <host pattern of the first matching restrict that omits the method>)`. The deny-only property is then structural. Intersection over matching restricts rather than first-match, because the order of `[[…]]` tables in a hand-written file should not decide what a host may do; deny-wins is the fail-closed reading and the README states it. An exception is scoped by its own host and path patterns, not by the restrict it lifts; the spec says so and shows the consequence. A redirect needs nothing: the client follows it with a new request, judged like any other.

**D4. Two rule prefixes and three hints.**
`method-block:<METHOD>` for the gate, `header-block:<guard>` (`upgrade`, `method-override`, `upgrade-response`) for the guards. Both follow the existing `stage:detail` convention, so the denial log's three-column format, `tjor denials`, the teardown recap and `_agent_rule` need no format change; a token has no whitespace or control byte, so the attacker-influenced method is safe in the tab-separated log, the 403 body and the `x-tjor-rule` header. The hints follow the fix: a `method-block:` line whose method matches the policy name grammar (`^[A-Z][A-Z0-9-]{0,31}$`) is widened by a `[[methods.except]]` rule or the restriction's `allow` list; a `method-block:` line whose method does not (`get`, `post`) cannot be written into a policy, so the hint says the client sent a non-standard method token and must be fixed; a `header-block:` line has no exception, and the hint says to leave the host unrestricted. `tjor denials` and the recap classify lines by these three patterns. A request whose method is literally `upgrade` is `method-block:upgrade` and gets the non-standard-token hint, never the guard's.
Alternative: a fourth log column — rejected: it changes a format two readers parse for one stage's benefit.

**D5. Call sites: the addon passes the raw method inside the headers-stage verdict; the CLI gains `--method` and a note; `tjor policy` parses it.**
`decide(url, method)` and `request_verdict(url, host, method)` take the method; the addon's `requestheaders` hook (PR #87) passes the ASCII-decoded raw bytes (D2). `tjor_policy.py check --policy P [--method M] [--json] URL`, default `GET`. When the URL's host is method-restricted (`method_restricted`), `check` reports it: in text mode one note after the verdict (the proxy also refuses protocol switches and method-override headers on this host, which the preview cannot see); under `--json` a boolean `header_guards` field and no prose, so the JSON stays parseable. `cmd_policy` in `bin/tjor` parses `--method <M>` and `--method=<M>` (a missing value is a usage error) next to `--explain`, forwards it, and the usage line shows it. The corpus gains a `method` field on every case (explicit, no loader default), method-denial cases, an exception case, an encoded-exception case, a lower-case case, a 32-character token case and a 33-character case; the parity test passes the method to all three call sites and the pytest id becomes `"<METHOD> <url>"`.

**D6. Header guards on restricted hosts, on the request and on the response, with no exception.**
In `requestheaders`, after an allowed verdict, if `tjor_policy.method_restricted(policy, judged_host)`: a request that asks for a protocol switch — an `Upgrade` header, an `upgrade` token in `Connection`, or a `Sec-WebSocket-Version` header, since mitmproxy keys its own WebSocket upgrade on that last header and not on `Upgrade` — denies with `header-block:upgrade`; any of `x-http-method-override`, `x-http-method`, `x-method-override` denies with `header-block:method-override`. In `responseheaders`, a `101` response on a flow whose judged host is restricted is refused before it reaches the agent: the flow is killed and the denial logged as `header-block:upgrade-response`, so an upstream that switches protocols without being asked cannot open a channel either (without the guard, mitmproxy would forward the `101` and then close the connection itself, or hand the connection to its WebSocket layer when the request carried `Sec-WebSocket-Version`). Deny rather than strip, so the agent and the operator see what happened (`tjor denials`) instead of a silently altered request. No policy rule lifts a guard: a host that legitimately needs WebSocket or override headers is simply not restricted, and the README and the spec say so in those words. Unrestricted hosts are untouched: the identity probes and ordinary WebSocket use on allow-listed hosts keep working. The matcher stays a pure function of (policy, url, method) — headers are not part of the parity corpus — so the CLI cannot preview these denials beyond the D5 note.
Alternative: an `upgrade = true` field on restrict rules — deferred: no use case yet, and it grows the expression language.

**D7. The gate lives inside the headers-stage verdict of PR #87.**
No new enforcement path: `request_verdict` gains the method and the guards slot into the same hook, so a method denial takes the 403-or-closed-connection route PR #87 defines and a streamed POST is refused before its first byte is forwarded. The `request` hook's fail-closed check (a verdict must have been recorded) covers the gate for free.

**D8. `augment_policy` validates first, re-emits from the parsed policy, adds POST exceptions for the gateway's POST inference paths; the launcher's contract covers a reused session directory.**
The augmentation calls `tjor_policy.parse_policy` on the base policy and raises on `valid=False` with the parser's errors. `ensure_topology` no longer copies the base policy first: with the gateway enabled it runs the augmentation on the base policy file and writes `${TJOR_SESSION_DIR}/policy.toml` from the output only when it succeeds; on failure it prints the augmentation's stderr, removes a session policy left by an earlier launch into the same directory (a derived file, regenerated at every launch, so nothing is lost), starts nothing, and says that sidecars still running from an earlier launch keep the policy they loaded until `tjor down`; without the gateway it copies as before. The session policy is serialised from the `Policy` dataclass — `mode`, `hosts`, `paths`, `methods` — never from a tolerant re-read, so nothing the parser accepted can be dropped and nothing it rejected can be silently healed. For each inference path that is POST in practice (`/chat/completions`, `/completions`, `/embeddings`, `/messages`, each with and without `/v1`) it adds `[[methods.except]] host = <gateway> path = <path> methods = ["POST"]` (idempotent, like the carve-outs). The gateway host is tjor's own sidecar whose policy the augmentation already defines in full, so defining its methods there too is consistent; a `host = "*"` restrict written for third-party hosts does not take down the harness's inference path. The management surface stays denied by the host block, which the gate never lifts. `gateway_test.sh` gains the launcher path in its own fresh directory (`mktemp -d`, since the existing test writes `policy.toml` into the shared one): `ensure_topology` in a subshell against a malformed base policy exits non-zero, prints the parser's error, and leaves no session policy; a second run with a stale `policy.toml` seeded beforehand ends with that file removed.
Alternative: let inference fail closed under a broad restrict — rejected: it is the worst first-hour failure, in tjor's own sidecar, for a rule the operator wrote for other hosts.

**D9. `tjor_policy_edit` distinguishes three shapes of the file.**
Find the `[hosts]` table header (`^\[hosts\]\s*$`, multiline). If absent: append a `[hosts]` table (unchanged). If present: look for `allow = [` within the lines that follow it up to the next table header (`^\[` or `^\[\[`); if found, insert after the bracket; if not, insert an `allow = [ … ]` key right after the `[hosts]` header. The old regex could run into a `[[methods.restrict]]` `allow` list, and stopping at the next header without the third case would append a second `[hosts]` table, which TOML rejects. The parse and semantic re-check stay as they are.

**D10. Proof: unit, parity, conformance on the PR #87 fixture.**
Unit tests in `test_policy.py` for every spec scenario, plus a property test: for every corpus URL and each of `GET HEAD POST PUT PATCH DELETE OPTIONS`, the verdict under the fixture policy either equals the verdict under the same policy with both method lists emptied (`dataclasses.replace`), or is a `method-block:*` deny where the stripped verdict allows. Addon tests in `test_addon_guards.py`: `request_verdict` with a method on a restricted host, the raw-bytes read, the three request markers and the override headers denied on `readonly.test` and forwarded on `allowed.test`, a `101` response killed and logged on a restricted host and untouched on an unrestricted one, a method literally named `upgrade`. Conformance: `images/conformance/policy.toml` restricts `readonly.test` to `GET`/`HEAD` with `POST` excepted on `/search` and on `/redirect`; the parity fixture carries the same rules; the echo answers `/redirect` with a `307` to `/items` and `/switch` with a `101` plus `Upgrade: websocket` whatever the request carried. Ten probes, each asserting the exact `x-tjor-rule` where a 403 is the expected answer: (1) "method gate: a write to a read-only host is denied" — POST `/items` → `method-block:POST`; (2) "method gate: a read on the read-only host reaches the upstream" — GET `/items` → the echo's 200; (3) "method gate: an exception admits the listed method on its path" — POST `/search` → 200; (4) "method gate: encoding cannot widen a method exception" — POST `/%73earch` → `method-block:POST`; (5) "method gate: a redirect does not carry a method past the gate" — POST `/redirect` → the `307` with `Location: /items` is asserted, the probe follows it with a POST → `method-block:POST`; (6) "method gate: a write inside a tunnel is judged on the tunnel target" — plain CONNECT to `readonly.test:8080`, inner GET with matching `Host` → 200, inner POST → `method-block:POST`; (7) "method gate: a write inside a TLS tunnel is judged on the server name" — the same through the TLS tunnel helper to `readonly.test:8443`; (8) "header guard: a protocol upgrade on a read-only host is refused" — GET `/ws` with `Upgrade: websocket` → `header-block:upgrade`, and the same with only `Sec-WebSocket-Version: 13` → `header-block:upgrade`; (9) "header guard: a method-override header on a read-only host is refused" — GET with `X-HTTP-Method-Override: DELETE` → `header-block:method-override`; (10) "header guard: a 101 from the upstream of a read-only host is refused" — GET `/switch` with no switch marker on `readonly.test` ends `closed()` with no `101` line read, `expect_denial("readonly.test", "header-block:upgrade-response")`, while the same GET on `echo-noinject.tjor-test` reads a `101` line (mitmproxy's own baseline). Every denial a probe provokes is declared through `expect_denial`, so the host-side count check of PR #87 covers them. The registry gains the ten names under `egress-policy`; CI's `conformance` job reports 40 probes.

**D11. Docs state the residuals; CHANGELOG; slides.**
README "Egress policy": the read-only API example (`GET`/`HEAD`, `POST` excepted on `/rest/api/2/search`), the read-only git example (`POST` excepted on `/*/git-upload-pack`, because fetch and clone POST there), the deny-only property, intersection of overlapping restricts, exception scope, the header guards (request and response; not previewable beyond the CLI note; never excepted — do not restrict a host that needs them), the 32-character method bound, the three hints, and the limits: the gate sees the verb, not what the request does, so a POST exception on a GraphQL endpoint admits mutations; listing `GET` admits neither `HEAD` nor `OPTIONS`; an exception is as wide as its path pattern and `*` spans `/`; CONNECT is decided on the host, each inner request on its method. README "LLM gateway": method rules survive augmentation, the gateway's POST paths are excepted, an invalid policy fails the launch and what that means for a reused session. `config/policy.toml`: the API example, commented out. CHANGELOG under `[Unreleased]`: Added (the gate, `--method`, the probes, the hints), Changed (augmentation and the launcher contract; `tjor policy add` anchoring; the API signature; bad-method and the 32-character bound). Slides: "A policy that can be bent" gets the method gate in its precedence line and a bullet with the residuals (verb only, GraphQL, HEAD/OPTIONS, `*`); "Policy has to see the request" mentions that the method is decided with the path; the ergonomics slide shows `--method` and the hints; the gateway slide says the inference paths survive method restrictions; all five pins updated. ADR 0012 (PR #87) needs no addition: the gate is a matcher stage.

## Risks / Trade-offs

- [An operator restricts a host the harness writes to, e.g. the LLM endpoint] → loud and specific: every request fails with `method-block:POST`, `tjor denials` shows it with the exception hint, `tjor policy <url> --method POST` previews it; the gateway host is excepted by construction; the README example restricts an API host, never a harness endpoint.
- [The gate is mistaken for a semantic read-only guarantee] → the README, the spec's limits requirement and the slide say the gate sees the verb and the named headers only, name GraphQL as the case where a POST exception admits writes, and the exception example uses a search endpoint because that is where POST-as-read is common.
- [A future call site evaluates without a method] → impossible by signature; the parity suite additionally fails if any call site disagrees on a method case.
- [Overlapping restricts or wide exceptions surprise an operator] → stated in the README and the spec (intersection; exception scope); `tjor policy --method` shows which pattern decided.
- [The Python API signature change] → in-repo callers only; all updated in the same change.
- [A relaunch into a reused session directory with a now-invalid base policy] → the stale session policy is removed, nothing starts, the message names the running sidecars' state; tested in `gateway_test.sh`.
- [The response guard kills a flow the upstream answered] → restricted hosts only, `101` only; the connection to the agent closes and the log says why.

## Migration Plan

Apply after `headers-stage-enforcement` (PR #87) is merged and this branch is rebased on `main`. Additive for policies: a file without a `methods` section is unaffected; `tjor policy <url>` without `--method` evaluates `GET`. Behaviour changes at the proxy are denials of requests no legitimate client sends (non-token or over-long methods). No data or config migrates. Rollback is reverting the change; a policy file carrying a `methods` section would then fail to parse (unknown top-level key) and deny everything — the loud direction.
