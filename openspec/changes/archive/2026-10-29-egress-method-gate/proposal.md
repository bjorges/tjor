# Proposal

## Why

Egress rules match host and path only: `tjor_policy.evaluate(policy, url)` never sees the HTTP method, and a rule entry has exactly the keys `host` and `path` (#66). Two consequences follow for anyone who brokers a credential into the cage. A token whose server-side scope is broader than the session needs — most SaaS API tokens carry the user's full permissions — cannot be narrowed to reads at the proxy, which is the one place tjor controls (ADR 0007: the agent holds a placeholder, the proxy holds the secret, so the proxy is where "read-only" has to be enforced). And "read-only" is not even expressible for APIs that query by POST (search endpoints commonly do): adding a method to the existing path rules would not help, because path allow carve-outs only rescue a host-blocked host and stage-2 path blocks have no exception mechanism. The result today is that a brokered credential is as powerful inside the cage as it is outside, and the only lever is to not broker it.

This change builds on `headers-stage-enforcement` (PR #87), which must merge first: it moves the verdict, the denial and credential injection to the headers stage, judges every request on the host its connection was opened to, keeps the proxy on HTTP/1.1, and gives the conformance suite an upstream fixture that records what reached it. The gate is one more stage of that verdict; without that change a streamed POST would be delivered before the gate could refuse it and a `Host` header could move a request to another host's rules.

## What Changes

- **A method gate in the egress policy.** A new top-level `methods` section with two rule kinds: `[[methods.restrict]]` (`host`, `allow = [<METHOD>, …]`) denies every method on a matching host that is not listed by every matching rule; `[[methods.except]]` (`host`, `path`, `methods = [<METHOD>, …]`) admits a listed method on exactly that path, matched like an allow rule (every encoded and decoded form of the path must match, charter L22). The gate runs **after** the existing stages, on a request they allow, and can only turn that allow into `method-block:<METHOD>`: a request the earlier stages deny is reported by the stage that denied it, a request the gate admits keeps the earlier verdict, and an absent `methods` section yields today's verdicts.
- **The method is an exact HTTP token.** It is compared byte for byte as the agent sent it — no case folding, no trimming — and must be an RFC 9110 token of 1 to 32 ASCII characters; anything else, a 33-character token included, is denied with `fail-closed:bad-method` on every host. `evaluate` takes the method with no default, so a call site that forgets it fails in the first test run instead of evaluating a POST as a GET. `evaluate_connect` is unchanged: CONNECT is decided on the host, and each request inside the tunnel is evaluated with its own method.
- **Header guards on restricted hosts.** On a host matched by a restrict rule, the proxy denies a request that asks for a protocol switch — an `Upgrade` header, an `upgrade` token in `Connection`, or a `Sec-WebSocket-Version` header (`header-block:upgrade`: a GET that becomes a duplex channel is not a read) — or that carries a method-override header (`header-block:method-override`), and refuses a `101` response from such a host before it reaches the agent (`header-block:upgrade-response`), so a non-compliant upstream cannot open a channel either. No rule lifts a header guard: a host that needs upgrades or override headers is not restricted. Unrestricted hosts are unaffected. The `header-block:` prefix keeps these apart from method denials, which have a different fix.
- **Every call site passes the method, and the parity suite checks it.** The addon passes the method as sent, inside the headers-stage verdict; `tjor policy <url>` gains `--method <M>` (default `GET`, so today's invocations keep their meaning) and, on a method-restricted host, notes that the header guards are not previewable (a field, not prose, under `--json`); the shared corpus carries a method on every case and gains method cases (charter L4). A method denial reads `method-block:<METHOD>` in the 403, the denial log and `tjor denials`, which, like the teardown recap, gives each kind of line its own hint: an exception or the restriction's `allow` list for a standard method, "fix the client" for a non-standard token such as `get`, and "leave the host unrestricted" for a `header-block:` line.
- **Policy tooling keeps the section intact.** The gateway's policy augmentation parses and validates the base policy with the policy parser first and re-emits the `methods` rules, adding POST exceptions for the gateway's POST inference paths so a broad restrict cannot break tjor's own inference host; the launcher writes the session policy only when the augmentation succeeds, removes a stale one left by an earlier launch into the same session directory, starts nothing, and says what an invalid base policy means for sidecars still running. `tjor policy add` inserts into `hosts.allow` only, never into a restrict rule's `allow` list.
- **Docs and proof.** A read-only-API example and a read-only-git example in the README and the packaged default policy (commented out, so the default verdicts do not change), with the stated limits; ten conformance probes for the gate, the redirect case, plain and TLS tunnels, and the three header guards, on the fixture PR #87 provides; the egress-policy, policy-ergonomics and llm-gateway specs amended and their slides re-read.

Compatibility. A policy without a `methods` section evaluates as before for every request whose method is an HTTP token of at most 32 characters. Two behaviours change for operators, both in the fail-closed direction: a request whose method is not an HTTP token, or is longer than 32 characters, is denied; a policy that fails to parse with the gateway enabled fails the launch rather than starting a deny-everything session. Breaking for the Python API only: `evaluate` and `check` require a method; every in-repo caller is updated.

### Modified Capabilities
- `egress-policy`: the precedence requirement gains the method gate as the final, deny-only stage; new requirements state the restriction and exception semantics, the exact-token method, the header guards on restricted hosts (request and response), and the stated limits; the fail-closed requirement covers a malformed `methods` section; the parity requirement's corpus carries the method.
- `policy-ergonomics`: `tjor policy <url>` accepts `--method` and notes the header guards on restricted hosts; the denial log, `tjor denials` and the teardown recap show the refused method or guard and give the right hint for each kind.
- `llm-gateway`: the session policy augmentation derives from the validated base policy and preserves every section, with a defined outcome for a reused session directory; the gateway's POST inference paths stay reachable under method restrictions.
