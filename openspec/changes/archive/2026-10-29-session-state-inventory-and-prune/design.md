# Design

## Context

See proposal.md — Why. What exists today, verified in `bin/tjor` and on a developer machine while the first draft of this change was reviewed, and shapes the approach:

- A session's state root is `<session.root>/<session-id>` (`resolve_session` in `bin/tjor`, default `~/.tjor/sessions`). The launcher writes `home/`, `profile/`, `policy.toml`, `Corefile`, `proxy-ca/`, `ca.pem`, `broker/`, `mask-empty/`, `gitcheck/` and the `denials.log`/`logvolume.log`/`secretscan.log` files there. Nothing records the workspace, harness or task the directory belongs to; only the container labels do, and they are gone once `gc` or `down` has run.
- `resolve_session`, which every session command calls, ends with `mkdir -p "${TJOR_SESSION_DIR}/home"` whether or not the caller is a launch. `cmd_down` works around it ("the empty home/ skeleton resolve_session just created" is not counted as a trace); `cmd_git_check` and `cmd_status` only test for files and need no directory.
- `preflight` runs before every command except `self-install` and `git-check` and dies when the daemon is unreachable. No lifecycle command runs without Docker.
- `cmd_run` proceeds: `resolve_session … launch` → `prepare_profile` (the first write into the state directory, `profile/`) → the `--dir` sensitive-path gates and the self-mount guard → `prepare_broker` (the mint) → gateway → secret scan → `resolve_agent_image` (may build) → a collision guard that refuses only a *running* agent → `ensure_topology` → `run_agent`, where `compose run -d` creates the agent container, then attaches. Nothing serialises two launches of one session, or a launch against a deletion of its state; `cmd_run` installs no trap.
- The collision guard and `cmd_reset`'s running check share the shape `docker ps … | grep -q .`, in which a failed query is indistinguishable from an empty result.
- `cmd_reset` owns the only definition of the `cache`, `sessions`, `creds` and `all` tiers (a bash `case`), refuses a running agent unless `--force` (which accepts the live-swap race), and passes every target through `ancestors_are_real_dirs` (charter L26: `rm -rf` follows a symlink in the path prefix).
- `cmd_gc` and `cmd_ls` discover sessions from container labels only, by design. `gc` reaps the containers of idle sessions; `down` removes a session's containers and runs the teardown git check.
- Git tamper detection keeps the baseline and the pending marker at `<state>/gitcheck/`; the spec says the marker clears only by a clean check or an acknowledgement.
- The launcher calls small helpers under `python/` (`tjor_cfg.py`, `tjor_gitcheck.py`, `tjor_safeprint.py`, …) and reads their output as lines or `\x1f`-separated fields — the same separator it uses for `docker ps` output, because a workspace path can contain anything else. There is no `jq`.
- Measured on a developer machine: 24 state directories, 22 820 entries, a full `lstat` walk takes 0.5 s. opencode's history lives eleven levels below the state directory (`home/.local/share/opencode/storage/…`), and a directory's mtime does not change when a file deep below it does, so any depth bound under-reports activity.
- macOS ships no `flock(1)`. `mkdir` is atomic on every filesystem tjor runs on and is the portable lock primitive.
- Credential files, from the session homes on that machine and the pinned packages inside the built images: tjor's own `broker/`, `proxy-ca/`, `ca.pem`; opencode `home/.local/share/opencode/auth.json`; `gh` `home/.config/gh/hosts.yml` (agent-minted, ADR 0007); Claude Code `home/.claude/.credentials.json` when a login happens in-cage, plus `home/.claude.json` and `home/.claude/backups/` which carry the account record; Copilot CLI resolves its token through `gh`/`GH_TOKEN` or a keyring library whose file fallback could not be located in the pinned package.
- The lifecycle integration suite runs live on the Linux engine in CI and is not a boundary-matrix probe suite, so new checks there need no registry entry.

## Goals / Non-Goals

**Goals:**
- An operator can see every state directory, what it belongs to, how stale it is, and whether it holds credentials, without reading `~/.tjor/sessions` by hand.
- Deleting state stays explicit, dry-runnable, refuses anything that has a container, and goes through the same symlink guard `reset` uses.
- A launch and a deletion of the same session's state cannot interleave.
- Lifecycle commands have no side effect on the state root.
- One definition of the state tiers, so `reset`, `ls --state` and `prune` cannot disagree about what a credential path is.
- No change to `gc`, `down`, the cage, the proxy or the images.

**Non-Goals:**
- Revoking brokered credentials from prune. Revocation is the proxy's teardown job (`down`/`gc`); a session with no containers has either been revoked already or lost its topology outside tjor. Prune forgets, exactly as `reset creds` does today, and the docs say so.
- Automatic or scheduled pruning, or a retention policy in config.
- Pruning anything outside `session.root` (the `~/.tjor/tmp` scratch of conformance runs, the install tree, user config).
- Backfilling metadata for legacy directories. They read as unknown; the next launch of that session writes the file.
- An inventory that works without the daemon. `preflight` requires it for every lifecycle command and this change keeps that.
- Locking `down` or `gc` against a launch. Both act on containers, which the lock does not cover; a launch racing a teardown is today's behaviour and unchanged.

## Decisions

**D1. A Python helper, `python/tjor_state.py`, owns the tier definitions, the inventory, the metadata write and duration parsing; bash owns the lock, the container checks and the deletion.**
Subcommands, all exiting non-zero with a message on any failure and printing nothing partial (results are built, then printed):
- `tier <name> <state-dir>` — the tier's paths as absolute paths, one per line; `all` is the directory itself.
- `inventory <root>` — one record per entry of the root, `\x1f`-separated: id, kind (`dir`, `link`, `other`), workspace or `-`, harness or `-`, last activity as epoch seconds or `-`, launch count or `-`, credential paths present (comma-joined, relative) or `-`. The root's `.locks` directory is skipped. Nothing behind a `link` entry is read.
- `meta-write <state-dir> --session … --workspace … --harness … [--profile-name …|--profile-dir …] [--task …]` — read-modify-write through a temp file created *inside the state directory* (so `os.replace` never crosses a filesystem), preserving `created`, bumping `launches`, setting `last_launch`, `schema: 1`. An unreadable existing file is replaced, not fatal.
- `duration <text>` → seconds, accepting `Nd`, `Nh`, `Nm`, `Ns`.
Why: the lstat walk, the metadata file and duration parsing are where a bash-only version would be either non-portable (`stat -c` vs `stat -f`) or wrong; the helper is unit-testable with `tmp_path`. `\x1f` fields rather than JSON because the launcher has no JSON parser and already splits docker output this way. Deletion, locking and the container check stay in bash because `ancestors_are_real_dirs`, `resolve_session` and the label queries already live there and are the audited code.
Alternatives: all-bash with `find -newer`/`stat` — rejected for portability and testability. Everything in Python including `rm` — rejected: it would duplicate the symlink guard the lifecycle suite already exercises.

**D2. `cmd_reset` reads its tier paths from the helper, and a helper failure is a hard stop.**
`tier_out="$(python3 "${TJOR_ROOT}/python/tjor_state.py" tier "${tier}" "${TJOR_SESSION_DIR}")" || die "state helper failed"`, then `mapfile -t paths <<<"${tier_out}"`. Never `mapfile < <(python3 …)`: a crashed helper would read as an empty tier and reset (or prune) would report success with the credentials still on disk. The refusal, dry-run and guard logic is unchanged, and the existing reset checks in the lifecycle suite (tier contents, symlink leaf, intermediate symlink refusal) guard the refactor.

**D3. "In use" means any container of the session in any state; a failed query is a refusal; the daemon is required.**
Prune runs `docker ps -a --filter "label=tjor.session=<id>" --format '{{.State}}'` with its exit status captured (`out="$(…)" || refuse`), never piped into `grep -q`. Any output refuses: an exited agent container still names `<state>/home` as a bind-mount source, `docker start` recreates a missing source as an empty root-owned directory, and a paused or created container holds its mounts. `tjor down` is the one path that removes a session's containers, and it runs the teardown git check on the way, so sending the operator there is the right default. No override. `ls --state` prints CONTAINERS as `running`, `stopped` (any other state) or `none`. The first draft's offline inventory (`?` when docker is down) is dropped: `preflight` dies before `cmd_ls` runs, and relaxing that for one flag is not worth a second preflight.

**D4. Last activity is the newest `lstat` mtime over the whole state directory, never following symlinks, floored by the recorded last launch; any read failure makes it unknown, and unknown never qualifies for `--older-than`.**
`os.walk(followlinks=False)` with an `onerror` handler, `os.lstat` on every entry including the directory itself. Why: legacy directories have no metadata and `home/` holds the harness history whose mtime is the honest signal, eleven levels down. The walk is bounded by nothing but the directory's size; measured at 0.5 s for two dozen directories and 23 000 entries, linear beyond that, and `ls --state`/`prune` are operator commands, not hot paths. Unknown-never-stale is the fail-closed reading: a directory tjor could not fully read is one it must not sweep by age.
Alternatives: a depth bound — rejected by measurement (opencode's history is below any sensible bound and directory mtimes do not propagate). Known harness leaf paths — rejected as brittle; they would need a per-harness list the images do not expose. Metadata only — rejected: says nothing for legacy directories, which are the ones that need pruning.

**D5. Exactly one selector; `--session` resolves like `reset`'s and never creates anything.**
`--older-than` and `--session` are mutually exclusive: both, or neither, is usage and exit 1 before any selection. Why not a union: `--session a --older-than 30d` would silently delete every old session *and* a fresh `a`, the worst footgun in the command; why not an intersection: a flag that sometimes selects and sometimes filters is a second footgun. Each `--session` value goes through `resolve_session` (short name qualified against the current workspace; a fully-qualified id of another workspace honored verbatim; the same idempotent rules as `down`/`reset`), so the ids `ls --state` prints paste back in — and after D11 that resolution creates nothing.

**D6. A pending git-check marker refuses whole-directory deletion unless `--discard-unreviewed`, which is accepted only with `--session`; `--creds-only` is not refused by the marker.**
`<state>/gitcheck/pending` existing means the baseline was never reconciled: deleting the directory destroys the evidence of cage-written git metadata the operator has not looked at. The refusal names `tjor git-check --session <id>` (and `--ack`) as the way out. The override is its own flag, not `--force`: in `reset`, `--force` means "accept the live-swap race"; here it would mean "destroy evidence", and one spelling for two risks invites the wrong habit. It is per session by construction — refused with usage next to `--older-than` — so an age sweep never discards evidence and the operator names each session whose findings they give up. `--creds-only` touches nothing under `gitcheck/`, so the marker does not refuse it. The git-tamper-detection spec gains this single exception to its clearing rule.

**D7. Metadata is written by `cmd_run` after every refusal and the broker mint, right before `ensure_topology`; the state directory is created by `cmd_run`, after the lock, before `prepare_profile`.**
A refused launch therefore never creates or touches metadata, and a relaunch updates it before the agent starts. The file is `meta.json` with `schema: 1`, `session`, `workspace`, `harness`, `profile` (`{"name": …}` or `{"dir": …}` or null), `task` (or null), `created`, `last_launch`, `launches`. It is not mounted into the cage and holds no secret. `tjor ls --state` and `prune` read it; nothing else depends on it, so legacy directories cost nothing.

**D8. Every deletion is guarded from the canonical configured session root.**
`root="$(cd "$(session_root)" && pwd -P)"` once per command; whole-directory prune checks `ancestors_are_real_dirs "${root}" "${root}/${sid}"`, `--creds-only` checks `ancestors_are_real_dirs "${root}" "${path}"` for each tier path — never from the session directory, which the first draft did and which would let a symlinked session directory pass. Canonicalising the root is safe because `session.root` is operator configuration outside every mount: the sensitive-path gate refuses mounting tjor's own session root into the cage, so nothing an agent does can swap a component of it, and refusing a root the operator deliberately placed behind a symlink would be a surprise with no security gain. Everything below the root is checked component by component as before. A refused path is reported with `loud`, the run continues, and the exit status is non-zero at the end so a script notices.

**D9. Output.**
`ls --state` prints a table: `SESSION  CONTAINERS  LAST-ACTIVE  WORKSPACE  CREDS`, sorted by session id, with `unknown` where a fact is unavailable (credentials last, unpadded: the list is never truncated), followed by one line per non-directory entry. `ls` without the flag is byte-for-byte unchanged. Prune prints one line per session with the verdict (`would remove` / `removed` / `refused: …` / `skipped: last activity unknown`) and the credential flags, "forgotten, not revoked" when a broker file goes, and "unreviewed git-check findings discarded" when `--discard-unreviewed` acted, so a dry run is a complete preview.

**D10. A per-session lock, held by launch from its first write until the agent container exists, and by prune and reset around check-and-delete.**
The lock is the directory `<root>/.locks/<sid>`, taken with `mkdir` (atomic, portable; macOS has no `flock(1)`), holding one file `owner` with `pid=<pid> cmd=<run|prune|reset>`. It lives beside the state directories, never inside one, so deleting a state directory cannot delete its own lock. Acquire: `mkdir` succeeds → write `owner`; `mkdir` fails → read `owner`; an empty or missing `owner` (the holder is between its `mkdir` and its write) or a pid that answers `kill -0` means held → refuse, naming the lock path and the owner line; a pid that does not exist means stale → remove `owner`, `rmdir` the lock, say so, and try `mkdir` once more. Release: remove `owner`, `rmdir`. `cmd_run` takes the lock right after `resolve_session` returns, before `prepare_profile`, installs an `EXIT` trap that releases it (every `die` after that point goes through it), and releases it explicitly in `run_agent` once `compose run -d` has returned the container id and the PTY check passed — from then on the container itself refuses prune (D3), and the lock must not stay held across an hours-long attach. `cmd_prune` takes it per session, immediately before the container query, and releases it after that session's deletion; `cmd_reset` the same around its deletion, with its `--force` semantics unchanged. A held lock refuses both directions; nothing waits. A test-only seam, `TJOR_TEST_HOLD_LOCK=<seconds>`, makes `run`, `prune` and `reset` sleep after acquiring, so the lifecycle suite can interleave them deterministically; it is read like `TJOR_ATTACH_DRY` and does nothing when unset.
Why not rename-then-delete instead: it protects the deletion from a racing agent but not a racing launch's fresh `home/`, mint and metadata from the deletion. Why `mkdir` and not Python `fcntl.flock`: the holder would have to be a process that outlives a bash function, and a lock held by a background process is harder to reason about than a directory with a pid in it.
Residual: a pid reused after a crash makes a stale lock look held. The refusal prints the lock path and owner line; the operator checks `ps` and removes the directory by hand. Fail closed, documented in the README.

**D11. `resolve_session` creates nothing; the launch path creates the state directory itself.**
The trailing `mkdir -p "${TJOR_SESSION_DIR}/home"` moves out of `resolve_session` into `cmd_run`, after the lock (D10). Every other caller (`down`, `reset`, `status`, `denials`, `git-check`, `ls --state`, `prune`) resolves the id only. `cmd_down` already treats a missing directory as "no state" and its comment about the skeleton goes; `cmd_git_check` warns "no baseline" and `cmd_status` tests `-s` on files, so none needs the directory.

## Risks / Trade-offs

- [The lock is held across `resolve_agent_image`, which may build images on a source tree] → a prune or second launch of that session during a first build is refused with "launch in progress (pid …)", and nothing waits. Acceptable: the alternative, taking the lock later, would leave `profile/` and the mint unprotected.
- [pid reuse after a crash] → see D10; refusal names the lock, operator removes by hand. The window is a crashed launch *and* the OS handing its pid to another long-lived process before the next prune — rare, and fail-closed.
- [A huge `home/` makes the walk slow] → linear in entries; measured 0.5 s for 23 000. A million-entry cache would take tens of seconds for one `ls --state`. The README says the inventory walks the state directory; no size is computed.
- [An agent writes continuously, so `--older-than` never selects its session] → correct: that session has a container and is refused anyway.
- [`--discard-unreviewed` per session is tedious with many unchecked sessions] → deliberate. `tjor git-check --session <id>` or `tjor down` per session is the path that keeps the evidence.
- [Operators expect prune to revoke] → the output says "forgotten, not revoked" when a broker file is removed, and the README states that revocation happens at `down`/`gc`.
- [The credential tier misses a harness location] → the tier names what the images are known to write; the README states that Copilot CLI's keyring fallback is not located and that whole-directory prune removes everything regardless. Adding a path is one list entry covering all three commands (D1).

## Migration Plan

None required. Legacy directories show as unknown until their session is launched again; a `.locks` directory appears under the session root at the first launch after upgrade. Rollback is removing the two commands and the lock; `meta.json` and `.locks` are inert to older launchers, which never read them (an older launcher does not take the lock, so it cannot be refused by one either).
