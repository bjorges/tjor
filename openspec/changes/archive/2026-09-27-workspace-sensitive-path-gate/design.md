# Design

## Context

See proposal.md — Why, and the delta spec under `specs/session-launch/`. Grounding in the repo (observed, `bin/tjor` at v0.18.17):

- `resolve_session()` (~L819) resolves `ws` from `git rev-parse --show-toplevel`, else `pwd -P` with a "not inside a git repository" warning; reads `session.root` via `cfg`; derives the session id; exports the identity set; and **ends with `mkdir -p "${TJOR_SESSION_DIR}/home"`** — a side effect that creates the state directory before `cmd_run` ever looks at `--dir`. It is shared by the launch path (`session_setup`, which passes a 4th arg `launch` and then mints broker material) and by `down`/`status`/`reset`/`denials` (no 4th arg, no minting).
- `dir_is_sensitive()` (~L960) is a pure function of one absolute path and `$HOME`. It knows nothing about `session.root` or the config dir. `~/.tjor` is not in its credential list.
- `cmd_run` parses `--unsafe-dir` into a local `unsafe_dir` **before** calling `session_setup`, but nothing passes that intent into `resolve_session`. The override is silent today: no warning is printed when it actually bypasses a refusal.
- The effective user-config file is `python/tjor_cfg.py: user_config_path()` — `$TJOR_USER_CONFIG`, else `$XDG_CONFIG_HOME/tjor/config.toml`, else `~/.config/tjor/config.toml`. The launcher already uses the `$XDG_CONFIG_HOME`/`~/.config` form for `policy.toml` (~L90, ~L1717).
- The entrypoint validates mount roots via `_norm_root` (refuses `/`, malformed spellings, wildcard forms) and cross-class overlap. It has **no** sensitivity check and no host context: inside the container `$HOME` is the agent's home, and neither the host home nor `session.root` nor the config dir is passed in.
- Tests: no test anywhere covers `dir_is_sensitive` or `--unsafe-dir`. The daemon-free `unit` CI job runs three mocked shell tests (`kube_test.sh`, `gateway_test.sh`, `conformance_runtime_test.sh`) that source `bin/tjor` through its `BASH_SOURCE` guard and call its functions directly. `gen_boundary_matrix.py` parses exactly two suite sources (`probes.py`, `landlock_test.sh`) and hard-fails on any registry drift.

## Goals / Non-Goals

**Goals:**
- Close the inversion: the workspace is subject to the same gate as `--dir`, evaluated **before** the state dir is created and before any credential is minted.
- Make a wrong resolution explainable: tell the operator *why* the workspace is `$HOME` when they launched from `~/notes`.
- Close the `~/.tjor` hole for every gate at once by teaching `dir_is_sensitive` the two tjor-owned roots.
- Prove all of it with a daemon-free test in the `unit` job and a row in the boundary matrix.

**Non-Goals:**
- Credential *files* inside a non-sensitive workspace (path rules cannot see them; #64 excludes this).
- A host-context sensitivity re-check in the entrypoint (impossible without host context — see Decision 6; overclaiming it would be worse than stating the limit).
- Changing what `--unsafe-dir` permits, or adding a workspace-only override flag.
- Reaping or inventorying session state dirs (#68).

## Decisions

1. **Gate inside `resolve_session`, only on the `launch` path, before `mkdir -p`.** The `launch` marker (4th arg) already distinguishes the launch path from lifecycle commands; the gate keys off it. Placing it in `resolve_session` — not `cmd_run` — is the only way to satisfy "before any state directory or topology is created": `mkdir -p "${TJOR_SESSION_DIR}/home"` is the last line of `resolve_session`, and `session_setup` mints broker material immediately after. *Alternative rejected:* gating in `cmd_run` after `session_setup` (where the `--dir` loop lives) would leave a state dir behind and may have minted a credential for a launch that is then refused.
2. **Pass the override as `TJOR_UNSAFE_DIR` (env-style global), set by `cmd_run` from `--unsafe-dir` before `session_setup`.** `resolve_session`'s positional signature is shared by five call sites; adding a 5th positional for a launch-only concern is noise. A single exported flag read only on the `launch` path keeps every lifecycle call site untouched. The existing `--dir`/`--dir-ro` loops keep reading their local `unsafe_dir` (unchanged behavior), and the same flag drives the new loud warning. *Alternative rejected:* a new `--unsafe-workspace` flag — the issue is explicit that `--unsafe-dir` remains *the* override, and two overrides invite the "which one did I mean" failure.
3. **`dir_is_sensitive` learns two more roots, with symmetric containment.** It reads the effective `session.root` (same `cfg session.root --default "~/.tjor/sessions"` + `~` expansion `resolve_session` already does; computed once into a global before the first call so the function stays a pure path check) and the effective config dir (`dirname "$TJOR_USER_CONFIG"` if set, else `${XDG_CONFIG_HOME:-$HOME/.config}/tjor`), both canonicalized with `pwd -P` when they exist (else used as spelled). For each, refuse when `p == root`, `root == p/*` (p is an ancestor), or `p == root/*` (p is under it) — component-boundary matches via the existing `"${x}/"*` pattern. Ancestor refusal is the new shape (the home check already does it for `$HOME`); descendant refusal matters because a session's own state dir holds `proxy-ca/`, `broker/`, harness auth. Putting this in the shared function means `--dir ~/.tjor/sessions` is refused for free, which the spec now states. *Alternative rejected:* checking the two roots only for the workspace — leaves the `--dir` hole open and splits one rule across two places.
4. **The git-climb explanation comes from data `resolve_session` already has.** `in_repo` is set when `--show-toplevel` succeeds; `git rev-parse --absolute-git-dir` is already called for the worktree probe. The message condition is: `in_repo` **and** `"$(pwd -P)" != "${ws}"` **and** the launch dir is not a repo root itself (which is implied — if it were, toplevel would equal it). Message: `<cwd> is not a repository; git resolved the workspace to <ws> via <gitdir> — launch from a repository (or pass --unsafe-dir)`. Otherwise (launch dir *is* the sensitive toplevel, or the `pwd -P` fallback) the plain refusal: `refusing to use sensitive host path as the workspace: <ws> (pass --unsafe-dir to override — this mounts it read-write into the agent)`. Both go through `die` (exit 1), matching the extra-dir refusals — this is an operator-input refusal, not a boundary-establishment failure, so `TJOR_EXIT_BOUNDARY` (90) is *not* used (its one reserved meaning, ~L23).
5. **Loud override warning, once, naming the path.** When `TJOR_UNSAFE_DIR` is set *and* the workspace was sensitive, `warn "--unsafe-dir: mounting sensitive host path <ws> as the workspace, READ-WRITE and git-trusted as a tree — every credential under it is exposed to the agent"`. No warning when `--unsafe-dir` is passed but nothing needed overriding (today's silence is fine then). The extra-dir loops gain the same one-line warning on an actual override, for consistency.
6. **Entrypoint: refuse only what it can judge; say so in the spec.** The entrypoint does not read `TJOR_WORKSPACE`; it receives every approved root — workspace included — through `TJOR_SAFE_DIRS`. So the refusal is applied to each normalized safe root: a system directory (`/etc`, `/usr`, `/var`, `/bin`, `/sbin`, `/boot`, `/sys`, `/proc`, `/dev`, `/root`, or a child of one — `/` is already refused by `_norm_root`) aborts with `TJOR_EXIT_BOUNDARY` like its neighbors, before any `safe.directory` registration. **Found during implementation:** without an override path in the cage, `tjor run --unsafe-dir` from a legitimate-but-listed workspace such as `/var/www/app` would pass the launcher's gate and then be refused by the entrypoint with no way through — two gates, one override. So the launcher's `--unsafe-dir` is forwarded to the agent service as `TJOR_UNSAFE_DIR` (compose env) and the entrypoint downgrades its refusal to a loud warning when it is set: the one override holds end to end. This is safe for the same reason the entrypoint check is only a misconfiguration guard: whoever bypasses the launcher already controls that environment. Home, credential dirs, session root, and config dir are host facts the container cannot see, so the spec states them as a **launcher** guarantee and forbids documentation from claiming an entrypoint re-check. *Alternative rejected:* passing `TJOR_HOST_HOME`/`TJOR_SESSION_ROOT` into the container so the entrypoint can re-check — an attacker who bypasses the launcher controls that env anyway, so the re-check would be theater, and it would leak host layout into the cage's environment for no enforcement gain.
7. **Coverage: a third suite source for the boundary matrix.** A new `tests/integration/workspace_gate_test.sh` sources `bin/tjor` (like `kube_test.sh`), builds a throwaway `$HOME` with a git repo rooted at it, and drives `resolve_session … launch` / `cmd_run` argument parsing with `HOME`, `XDG_CONFIG_HOME`, `TJOR_USER_CONFIG`, and a `config.toml` `session.root` override under a temp dir. It needs neither git-remote nor Docker: every refusal fires before the first `docker` call. It runs in the `unit` job. `gen_boundary_matrix.py` gains a `WORKSPACE_GATE` suite constant, a `WORKSPACE_GATE_FILE`, reuses `parse_landlock` for its `check "…"`/`ok "…"` lines, and gets one rendered `session-launch` row (`Sensitive host path refused as the primary workspace`) plus `boundary=False` acknowledgements for the functional checks (override warning, normal-repo path, lifecycle exemption). `docs/boundary-matrix.md` is regenerated; the drift check keeps it honest. *Alternative rejected:* putting the checks into `landlock_test.sh` — that suite needs a Landlock-capable live engine and does not run in the `unit` job; the gate is a pure launcher check and belongs in the cheap job.

## Risks / Trade-offs

- [Breaking for people who legitimately launch from `$HOME`-rooted dotfiles repos] → deliberate (#64 "Breaking by design"); `--unsafe-dir` is the documented, loud path; CHANGELOG marks it **BREAKING** and the error names the flag.
- [`pwd -P` canonicalization of `session.root`/config dir when they do not exist yet (first run)] → fall back to the spelled path with `~` expanded; the comparison is still on component boundaries. A symlinked session root is canonicalized when present, matching how the workspace and extras are already compared (v0.17.1 re-review).
- [Ancestor refusal could bite a mono-directory layout, e.g. workspace `/srv/work` with `session.root = /srv/work/.tjor`] → correct to refuse (the workspace would contain every session's CA/broker material); the message names the containing root so the operator can move `session.root`.
- [Lifecycle commands skip the gate, so `tjor down` in `$HOME` works] → intended: refusing teardown would strand sessions launched under `--unsafe-dir`; lifecycle commands mount nothing.
- [Entrypoint cannot re-check host-context sensitivity] → stated in the spec as a launcher guarantee; no false claim in docs or the matrix (the matrix row's suite is the launcher test, not the cage).
- [`dir_is_sensitive` now depends on two globals] → computed once in a small `init_sensitive_roots` helper called by `resolve_session` (launch path) and `cmd_run`; the test sets them via the same helper so there is one derivation.

## Migration Plan

Additive code plus one refusal; no config schema change. A patch release is enough despite the **BREAKING** label (pre-1.0 policy), with the CHANGELOG stating: launches whose workspace resolves to a sensitive path now abort; pass `--unsafe-dir` to keep the old behavior, loudly. Rollback is a plain revert. Existing sessions are untouched (their state dirs and containers are unaffected, and `down`/`reset` keep working from the same workspace).

## Open Questions

None that change the specs, approach, or tasks. Whether the entrypoint's system-directory list should later be unified with the launcher's (one source of truth via an env-passed list) is a follow-up nicety, not a correctness question.
