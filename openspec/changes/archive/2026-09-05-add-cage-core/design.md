# Design: add-cage-core

## Context

Greenfield repo; the constraints are ADR 0004 (design baseline) and `docs/clean-room-charter.md` (operational lessons, cited below as L*). The build is clean-room per ADR 0003: OSS components + charter + first principles only. Development host is macOS (Colima available); target runtimes for the core tier are any Docker engine (Desktop, Colima, Linux, WSL2).

## Goals / Non-Goals

**Goals:**
- Smallest complete vertical slice: launch → harness works inside the cage → boundary provably holds.
- Every guarantee falsifiable: conformance probes (GitHub #13) exist for each spec requirement from day one.
- Conventions later deltas (D1–D4) plug into: config layout, state-dir layout, proxy addon slot.

**Non-Goals:**
- Session identity, broker, GC/attach, gateway (D1–D4 — own changes).
- LSM hardening add-ons (own change; the launcher's tiered-guarantee reporting lands now, the AppArmor content itself later).
- Multi-arch image publishing, brew distribution.

## Decisions

- **Compose over hand-rolled `docker network`/`run` scripting.** Declarative topology (named internal network, sidecars, profiles) is more maintainable and shareable; the one ordering constraint compose can't express directly — proxy created on the egress network first, connected to the internal network second (L28) — is handled by the launcher post-up step and asserted by a conformance probe. *Alternative:* pure bash topology scripts — rejected as the known-maintenance-burden path.
- **mitmproxy as the egress proxy, explicit mode.** Python addon API gives the policy engine a natural home and later a D1 verify/strip slot; explicit mode (`HTTP(S)_PROXY`) is what CLIs expect and needs no iptables (ADR 0004). *Alternative:* Squid — mature ACLs but a weaker addon story for the D1/D2 roadmap; tinyproxy — too little policy surface.
- **CoreDNS as the DNS sidecar.** Zone-scoped forwarding with local NXDOMAIN for everything else (L21) is straightforward in its config model; policy-derived zone list is generated by the launcher from the same policy file the proxy reads (single source, L4/L19). *Alternative:* dnsmasq — workable, weaker config generation story.
- **Policy engine as a single Python module** vendored into the proxy addon and invoked by the launcher/debug CLI through one code path, with a verdict-corpus parity test (L4). Encoding-aware asymmetric matching per L22. *Alternative:* reimplement the matcher per component — the exact drift failure L4 warns about.
- **Launcher in Bash (≥4.4) with strict preflight (L20), config merged via one function (L19).** A Go/Rust binary is attractive later (brew story) but premature; the launcher's contract is specified, so a rewrite stays behavioral no-op. First harness: opencode; Claude Code and Copilot CLI as image build toggles once the slice works.
- **State layout:** `~/.tjor/sessions/<session-id>/` holds harness XDG dirs (bind-mounted, L14) and metadata; images never contain state. Same-path workspace mounting via `git rev-parse --show-toplevel` (L15).
- **Conformance suite as its own container** on the agent network, runnable by CI and by `tjor doctor`; probes map 1:1 to spec scenarios.

## Threat-model boundaries (from the 2026-09-05 external review)

- **Docker API users are trusted.** The core-guarantee check (internal-only network) runs at launch; nothing re-verifies it live, so a host actor with docker-socket access could reconnect networks afterward (TOCTOU). That actor is root-equivalent on the host and can defeat any launcher check — continuous re-verification is a D3/GC-loop candidate (issue #10), not a v0.1 boundary.
- **Launcher/entrypoint self-integrity is delivery's job, not runtime's.** The scripts are distributed via git (and later a signed brew formula); a self-checksum is theater against an attacker who can modify the script, since they can modify the checker. The checksum gates protect *downloads into images* (charter L23), which is the claim the docs make.
- **CONNECT defer-tunnels terminate at mitmproxy.** ~~No TLS/TCP passthrough is configured~~ **Correction (2026-09-05 re-review): this claim was wrong as originally written** — mitmproxy's `rawtcp` option defaults to TRUE, so unclassifiable byte streams in a tunnel were relayed raw, bypassing request-stage policy. Fixed by `--set rawtcp=false` in the proxy command, and a conformance probe now smuggles non-TLS/non-HTTP bytes through a tunnel and asserts they never reach the upstream. The lesson stands in both directions: an accepted-risk claim about a default must be verified against the running config, not the design intent.
- **The resolved-address guard has a residual TOCTOU**: the addon checks resolution at verdict time, mitmproxy re-resolves at connect time; a rebind inside that window is possible — and the window is the full guard-cache TTL (now 10s), not "sub-second" as this note originally understated. Closing it fully means pinning the connect address to the checked one (candidate follow-up in issue #10).

## Risks / Trade-offs

- **Harness-vendor endpoint split (allow function, block telemetry) is empirical** and may break on harness updates → conformance/regression run covers "harness still does real work" (proposal §2.3 lesson); policy is data, fixable without release.
- **Explicit-proxy env is advisory for badly-behaved tools** — irrelevant to safety (the internal network is the guarantee; a bypassing tool just fails) but can confuse users; `tjor doctor` explains denied traffic.
- **Corporate TLS interception environments (L6)** need a CA-overlay hook in the image build; deferred until first user hits it, tracked in the policy config design.
- **WSL2/Desktop behavioral differences** for internal networks are asserted by the conformance suite rather than assumed; if a runtime can't hold a core guarantee, tjor refuses to run there (loud, per spec) — a support-matrix trade-off accepted for v0.1.
